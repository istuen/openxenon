# What

**v0.4 的核心命题**：

1. **技术基座**：`.md` 解析从 hybrid（unified + 自研 md-bridge 10252 行）迁移到 **unified-native**（unified 生态原生插件）；`.oxn` 仍走 **langium**。md-bridge 减到 ~3500 行（-66%）。

2. **资产层减法（5 项决策）**：
   - **Q1 拒绝合并**：Domain + Blueprint 保持两文件，**不**引入 `oxn intent init` 脚手架
   - **Q2 软推荐**：在 domain.md 新增可选 `## Stack` H2（不填不报错）
   - **Q3 维持现状**：frozen.json 物理位置不动（已在 `proofs/<p>/frozen.json`）
   - **Q4-A 采纳 + Q4-B 拒绝**：`oxn proof run` 时拷贝 work.md → proof.md（immutable 快照 + work-hash.txt）；**不**支持"无 domain/blueprint 的 proof work"
   - **Q5 同意内联**：task 内联进 work.md（`## Tasks` 下 H3 = task），删 `tasks/` 目录

3. **目标产物**：
   - `src/oxl/md-bridge/` 10252 → 3500 行
   - `src/oxl/md-pipeline/` 新建（unified-native 入口 + 5 unified plugins）
   - 4 PR 串行 + 1 发布 PR

# Why

## 1. 现状矛盾

### 1.1 技术债务：md-bridge 半吊子

`src/oxl/md-bridge/`（10252 行）当前用 unified 把 markdown 解析成 mdast（✓ 标准），但**之后**的所有 OpenXenon 逻辑（提取 / 验证 / 编译 / 注册 / driver 切换）都是自研的"小 reinvent"。

| 自研层 | 行数 | 已有 unified 生态等价物 |
|---|---|---|
| `extract-headings.ts` | 237 | `mdast-util-find` + `mdast-util-visit` |
| `extract-list-fields.ts` | 302 | `mdast-util-visit` + List 节点遍历 |
| `mdast-validator.ts` | 334 | `unified` plugin / `remark-lint` config |
| `mdast-to-kernel.ts` | 417 | unified transformer |
| `driver-registry.ts` | 110 | 删（按后缀显式分支）|
| `entity-registry.ts` | 111 | plugin array（更轻）|
| `compilers/*.ts` | 1892 | 5 unified transformer plugins |
| `oxl-md-*.ts` | 1220 | `unified().use(plugin).stringify()` |
| **合计** | **6286** | （除 md-pipeline 入口 / mdast-util-oxn / stringifier 之外全部可消解）|

**这是工程上的明确浪费**：生态早就有标准实现，OpenXenon 自己又写了一份。

### 1.2 资产层 IAP 闭环风险

v0.3.4 的 proof 机制存在 2 个边界问题：

- **proof 验证 live work.md** — AI 改了 work.md 后，proof 仍验证"老 work.md + 新 frozen.json"的不一致快照，证据稳定性依赖 planLock 4 hash 守卫
- **proof 不持有不可变快照** — proof 验证时读的 work.md 是被改过的版本，与 proof 创建时的 work.md 可能不同

**架构核心矛盾**：proof 的"判决"应该是对**某一时刻 work 状态的不可变验证**，而不是对**持续变化的 live 状态**的实时校验。

### 1.3 工程仪式感过重

v0.3.4 的 v1.1 8 阶段 work 流程（create / add-task / validate / lock / run / submit / status）有 2 个环节对 AI 自动化不友好：

- **`add-task`** — 仪式性步骤，每加一个 task 需单独 `oxn work add-task`
- **`lock` + `planLock` 4 hash** — 强一致性保护过度（AI 修改 work 是合理的协作模式）

## 2. 减法的边界（核心约束）

**减法不能破坏 IAP 三轴分离**：

- **Intent** = 业务 Intent（domain/blueprint），不合并（Q1 拒绝）
- **Align** = work 编排，可简化（Q5 同意内联）
- **Proof** = 证据，不退化成"无意图约束的裸探针"（Q4-B 拒绝）

**减法也不能丢失证据稳定性**：

- proof.md 不可变快照 = work.md 在 submit 时的 byte-equal 副本
- work-hash.txt = 快照的 SHA-256，用于后续 hash drift 校验
- AI 修改 live work.md 不影响已存 proof.md（隔离边界）

## 3. 6 条设计原则

| # | 原则 | 来源 |
|---|---|---|
| 1 | Domain + Blueprint 分开 | Q1（保持现状） |
| 2 | Stack 内联 `## Stack` H2（软推荐） | Q2 |
| 3 | frozen.json 物理位置不动 | Q3 |
| 4 | Proof 仍需 domain/blueprint 引用 | Q4-B 拒绝 |
| 5 | task 可内联 work.md（snapshot + hash 自洽） | Q5 + Q4-A |
| 6 | `.md` → unified-native；`.oxn` → langium | 技术基座 |

## 2. Proof 证据机制（Q3 + Q4-A + Q5 闭环）

### 2.1 提交流程（手动，on `oxn proof run`）

```
AI 在 work.md 上做修改（可任意改 task/part/probe）
        │
        ▼
  oxn proof run <proof-name>
        │
        ├─→ 1. 计算 work.md 当前 SHA-256 = H_live
        │
        ├─→ 2. 读 proofs/<p>/work-hash.txt 中 H_prev（首次跑时不存在）
        │     ├─ 首次 / 不一致 → 走步骤 3
        │     └─ 一致 → 跳过拷贝（走 5）
        │
        ├─→ 3. 拷贝 work.md → proofs/<p>/proof.md（immutable, 0o444）
        │
        ├─→ 4. 写 H_live → proofs/<p>/work-hash.txt
        │
        ├─→ 5. 跑 proof.md 内 probe 列表，生成 frozen.json
        │
        └─→ 6. return frozen.json 路径
```

### 2.2 Hash 校验时机

| 触发 | 行为 | 错误码 |
|---|---|---|
| `oxn proof run` 之前 work.md 未变 | 复用旧 proof.md + frozen.json | — |
| `oxn proof run` 时 work.md 变更 | 拷贝新快照 + 跑新 probe | — |
| `oxn proof verify`（新命令） | 重新 hash work.md 与 H_prev 比对 | `E_PROOF_WORKHASH_DRIFT` |
| `oxn proof show` 读 proof.md | 不读 live work.md（隔离） | — |

### 2.3 关键约束（Q4-B 拒绝路径）

- ❌ **不**支持"创建无 domain/blueprint 的 proof work"（破坏 IAP 闭环）
- ✅ Proof 仍需在 proof.md frontmatter 声明 `proofs-target-domain` + `proofs-target-blueprint`
- ✅ 验证能力 = 边界 (term/ban) + 路径 (blueprint slot) + artifact (probe) 三重
- ✅ Proof First 仍可先建 proof（声明期望 verdict 标准 + 引用），反向驱动 work 产出

## 5. 关键设计权衡

### 5.1 Trade-off 1：Stack 软推荐 vs 硬要求

| 维度 | 软推荐（选） | 硬要求 |
|---|---|---|
| 强制力 | 文档约束 | E_DOMAIN_STACK_MISSING 报错 |
| 过渡成本 | 低（旧 domain 不破坏） | 高（旧 16 domain 需补 Stack） |
| 工程师接受度 | 高 | 中（强制填写） |

**选软推荐**：避免破坏 16 个旧 domain；UX 渐进

### 5.2 Trade-off 2：保持现状 vs `oxn intent init` 脚手架

| 维度 | 保持现状（选） | 脚手架 |
|---|---|---|
| 命令数 | 2 (`domain create` + `blueprint create`) | 1 (`intent init`) |
| 心智模型 | 1 entity = 1 文件 | 1 intent = 2 文件 |
| 错误恢复 | 独立删除/重命名 | 需联动维护 |

**选保持现状**：user 明确要求；旧流程零破坏

### 5.3 Trade-off 3：手动快照 vs watcher

| 维度 | 手动（选） | watcher |
|---|---|---|
| 触发器 | `oxn proof run` | work.md 任意修改 |
| Daemon 依赖 | 否 | 是（需 server.ts watcher） |
| 快照成本 | 单次 | N 次（每次保存） |
| 概念简洁 | 高 | 中（隐式副作用） |

**选手动**：避免 daemon 依赖；snapshot 一次性动作更明确

### 5.4 Trade-off 4：自动迁移 vs 双轨

| 维度 | 自动（选） | 双轨 |
|---|---|---|
| 旧 works 处理 | 一次脚本转 | 长期共存 |
| 代码复杂度 | 低（无兼容路径） | 中（双路径判断） |
| 数据一致性 | 强（统一格式） | 弱（混合格式） |

**选自动**：`oxn work migrate <w>` 一次脚本全量转；保留 `.migrated-v0/` 备份

### 5.5 Trade-off 5：proof.md AS-IS 拷贝 vs 规范化

| 维度 | AS-IS 拷贝（选） | 规范化（统一格式） |
|---|---|---|
| 字节级稳定 | 严格 | 视规范化而定 |
| 反向追溯 | 易（diff proof.md vs work.md） | 难（规范化已变形） |
| 工具友好 | `git diff` 直接看 | 需 re-canonicalize |

**选 AS-IS**：hash 校验是唯一真理标准，规范化增加回溯成本

- v0.4.0 不实现 stack 硬要求（Q2 决策：软推荐）

# 决策记录

| # | 决策 | 选项 | 理由 |
|---|---|---|---|
| D1 | Q1：domain/blueprint 是否合并 | **保持现状（不合并）** | DDD 分离（Intent = 业务 / Align = 骨架）；user 明确反对合并 |
| D2 | Q2：Stack 是否拆为独立实体 | **内联 `## Stack` H2（软推荐）** | Stack 是 Intent 语义约束，非 Align 骨架；避免 5 类实体膨胀 |
| D3 | Q3：frozen.json 是否挪到 proof | **不动** | 物理位置已在 `proofs/<p>/frozen.json`；区分 task 快照会破坏 IAP 三轴分离 |
| D4 | Q4-A：work.md 快照成 proof.md | **采纳（on `oxn proof run`）** | 不可变快照是证据稳定性的关键；与 hash drift 校验形成闭环 |
| D5 | Q4-B：Proof First 是否免 domain/blueprint | **拒绝** | 无意图约束的 proof 退化为"裸探针检查"；破坏 IAP 闭环 |
| D6 | Q5：task 是否内联 work.md | **同意（`## Tasks` H2 + H3 = task）** | task.md 在 v0.3 已冗余；snapshot 机制化解"AI 改 work.md"风险 |
| D7 | Q5 migrate：旧 28 works 迁移策略 | **自动（1 次脚本）** | 避免双轨长期共存；保留 `.migrated-v0/` 备份 |
| D8 | Q4-A 触发时机 | **手动（仅 `oxn proof run`）** | 避免 daemon 依赖；snapshot 一次性动作更明确 |
| D9 | proof.md 内容形式 | **AS-IS 拷贝（不规范化）** | hash 校验是真理标准；规范化增加回溯成本 |
| D10 | unified major 版本 | **保持 v11（不升 v12/v13）** | v0.4.0 范围已大；major 升级推迟 v0.5 |

# 范围之外

下列功能在 v0.4.0 **不**实施，明确推迟：

1. **149 legacy `:::intent` 迁移**：v0.3.0 PR-B 已强制 `E_MD_DEPRECATED_SYNTAX`，但旧 149 fixture 仍在 `.openxenon/forges/` 与历史池中。v0.4 不重做，v0.5 视情况统一迁移。

2. **Watcher 模式自动快照**：当前 v0.4 决策为手动触发（`oxn proof run`）。Daemon 模式 + watcher 自动写 proof.md 推迟 v0.5+。

3. **`oxn intent init` 脚手架**：user 在 Q1 决策中明确反对（保持现状）。不再考虑。

4. **Stack 硬要求**：Q2 决策为软推荐。不引入 `E_DOMAIN_STACK_MISSING` 守卫。

5. **unified v12/v13 major 升级**：v0.4 保持 v11。v0.5 视生态情况评估。

6. **proof 跨 work 引用**：当前 proof 物理绑定 work-hash；不支持 proof 跨 work 共享。v0.5 视需求评估。

7. **task 跨 work 复用**：task 内联 work.md 后跨 work 复用仅通过 blueprint slot（user Q5 决策）。不支持独立 task.md 复用。

8. **Langium schema 升级**：oxn.langium 语法不在 v0.4 范围。v0.5 视情况扩 `## Stack` / 内联 task 等。
