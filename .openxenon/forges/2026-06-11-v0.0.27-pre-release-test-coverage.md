## 1. 背景与动机

### 1.1 第一版发布决策

> **第一版（Proof-First + Work v1.1）可发布**。
> **Daemon / Hall / Cache / GC / Export / Explore 留到 v0.2 强化阶段**。

依据详见前置审计文档 §6。本 PR 的目的是**在发布前补齐稳定性硬卡点**，确保 Proof + Work 双闭环在 v0.0.27 标签下的可靠性。

### 1.2 痛点：5 层测试覆盖不均

审计发现 L0 / L1-OXL / L2 / L3 已**足够支撑第一版**，但 L1 Infra 有 **1 个硬卡点** + **2 个软缺口**：

| 类型 | 模块 | 危险度 | 是否阻塞发布 |
|---|---|---|---|
| 🔴 硬卡点 | `src/infra/frozen/immutable.ts` | 🚨🚨🚨 | **是** |
| 🟡 软缺口 #1 | `src/kernel/verdicts/catalog.ts`（SSOT 测） | 🚨 | 否（建议补） |
| 🟡 软缺口 #2 | `src/infra/probes/`（6 个常用 probe 单测） | 🚨🚨 | 否（建议补） |

### 1.3 为什么是单 PR 多任务

5 个任务互相独立但**同主题（发布前补测）**、同审查窗口（架构师 + 维护者同批评审），合并到 1 个 PR：

| 理由 | 说明 |
|---|---|
| 主题单一 | 都是"补单测"，不引入新功能 |
| 评审集中 | 1 次评审，5 个子任务 |
| 易于回滚 | 任何一个失败都可单独 revert（commit 分粒度细） |
| changelog 单一 | 1 个版本号 + 1 条片段 |

## 3. 范围与硬卡点

### 3.1 1 个硬卡点（必补）

**`src/infra/frozen/immutable.ts`** — IAP 第一法则"证明不可绕过"的物理基础。

| 风险 | 后果 | 现状 |
|---|---|---|
| 写路径 `try/finally` 回锁 0o444 改错 | chmod 不生效 → frozen.json 可被 AI 篡改 | 0 单测 |
| 验签逻辑（SHA-256 比对）改错 | 篡改的 frozen.json 仍被接受 | 0 单测 |
| 覆盖场景临时抬位（0o444 → 0o644）改错 | writeFileSync 抛 EACCES | 0 单测 |
| schema 校验失败处理改错 | 错误体被误判为合法 | 0 单测 |

**影响面**：Proof-First 闭环 + Work v1.1 闭环共用此写盘入口。
**发布阻塞度**：🔴 **直接阻塞**（IAP 不变量无回归保护）。

### 3.2 2 个软缺口（建议补）

**软缺口 #1：`src/kernel/verdicts/catalog.ts`** — AI ↔ internal 翻译的**单 SSOT**。

| 风险 | 后果 | 现状 |
|---|---|---|
| 增删一条 catalog 改错 | 5+ 处复用点（`proof.ts` / `proof-runner` / `proof-frozen-writer` / `cli/proof.ts` / `cli/work.ts`）行为漂移 | 0 专门测 |
| `inputMap` 翻译错 | AI 写的 `path` 字段映射到 internal `pattern` 字段失败 | 0 专门测 |

**影响面**：Proof-First 闭环（catalog 是 AI 看到的语义层与 OXN 内部实现层的唯一桥）。
**发布阻塞度**：🟡 **不阻塞**（e2e `proof.test.ts` 间接覆盖 happy path），但补测成本极低（半天）。

**软缺口 #2：`src/infra/probes/` 6 个常用 probe 单测** — 物理观测的执行者。

| 风险 | 后果 | 现状 |
|---|---|---|
| 18 个 probe 中 17 个零单测 | 改坏某个 probe handler，e2e 不一定跑到 | 1/18 测覆盖（仅 `ts-compiles`） |
| catalog `describe` 描述与 handler 实际行为漂移 | AI 不知道 probe 真正接受什么 | 无 SSOT 校验 |

**影响面**：所有 Proof run + 所有 Work 探针执行。
**发布阻塞度**：🟡 **不阻塞**（生产前手动冒烟 6 个最常用即可），补测可平滑降风险（1 天）。

## 12. 决策记录（ADR）

### ADR-001：硬卡点修复走"单 PR 多 commit"模式

**决策**：5 个任务分 5 个 commit，合并到 1 个 PR。

**理由**：
- 主题单一（补测），便于评审
- 每 commit 独立可 revert
- 1 次评审覆盖 5 个子任务
- 1 条 changelog 片段

**替代方案**：
- 5 个独立 PR — 增加评审负担 5 倍
- 1 个大 commit — 失去粒度回滚能力

**决策者**：架构师 + 维护者

### ADR-002：本 PR 严格不修改产品代码

**决策**：仅新增 `*.test.ts` + `.changes/*`，不修改任何 `src/` 下的产品文件。

**理由**：
- 补测时发现 bug → issue 化 / 后续 PR
- 避免 PR 范围蔓延
- 评审聚焦"测试质量"而非"代码变更"

**例外**：若 T1/T2/T3 实施中发现**无法通过测试的现有 bug**（如 catalog 字段缺失），则 PR 拆为 2 个：bugfix PR（最小改动）+ test PR（本 PR）。

**决策者**：架构师 + 维护者

### ADR-003：测试补到"补到恰好"而非"补到 100%"

**决策**：本 PR 只补 1 硬卡点 + 2 软缺口，**不追求 100% 覆盖**。

**理由**：
- 18 个 probe 全部单测需 1-2 周，本 PR 范围失控
- L2 Work 状态机单测已在 backlog，发布后持续补
- L1 Infra 其他 14 个零测模块不在本 PR 范围

**红线**：发布阻塞的 1 个硬卡点必须修；其他按"价值/成本"评估。

**决策者**：架构师 + 维护者

### ADR-004：发布阻断 vs 软补的明确边界

**决策**：

| 类型 | 是否阻塞 v0.0.27 发布 |
|---|---|
| 硬卡点（`infra/frozen/immutable.ts`） | **是** |
| 软缺口 #1（catalog SSOT） | 否（建议补） |
| 软缺口 #2（6 个 probe 单测） | 否（建议补） |
| 其他缺口 | 否（backlog） |

**含义**：
- T1 必须合入 v0.0.27 发布前
- T2 / T3 可独立合并到 v0.0.27 / v0.0.28
- 发布策略：**T1 必合**，**T2 / T3 推荐合**

**决策者**：架构师 + 维护者
