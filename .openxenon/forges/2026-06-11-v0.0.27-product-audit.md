## 3. 独立性 / 闭环性结论

### 3.1 **独立闭环的"子产品"**（可单独成立）

1. **`oxn proof` 闭环** — 5 子命令 + 1 反馈（`insight`），输入只有"语义 probe 名 + JSON 输入"，产出 `frozen.json`；不依赖 Domain / Blueprint / Work / Task。**这是真正的 PMF 入口**。
2. **`oxn work` 闭环** — 15 子命令，完整 work/task 状态机，依赖 Blueprint（可选 Domain）。
3. **`oxn init + install-skill`** — 0 配置、0 外部依赖，可以直接 `oxn` 起来就能用。
4. **`oxn domain`** — 完全独立。
5. **`oxn blueprint`** — 完全独立。
6. **`oxn dev`** — 完全独立（DSL 内部工具）。

### 3.2 **不够独立 / 互相依赖**

- `proof` 完全独立 ✅
- `work` 依赖 `blueprint`（必须先有蓝图才能 `work create`）— **设计上合理**
- `insight` 依赖 `proof run` 产生的 `frozen.json` + `probe-stats.json` — **设计合理**
- `daemon` / `hall` / `cache` / `gc` / `export` / `explore` — **未挂载，无法形成闭环**

### 3.3 **作为产品：60% 闭环已可发布**

**可发布**：
- `oxn init + install-skill + proof`（5 子命令 + 1 个 insight）— README §4 推的 5 分钟体验，**已完整**。
- `oxn work v1.1 8 阶段流程`（15 子命令）— 完整但**复杂度高**（work.ts 2832 行），需 5 个 e2e 才能跑通。

**不可发布**（代码在但挂不到 CLI）：
- Daemon：**stop 是 stub**（`daemon-stop.ts:9` `console.log('TODO: 实现 daemon stop')`）
- Hall：`hall` / `global hall` / `global` 三个命名空间全部未挂载到 `index.ts`
- 工具命令：`cache` / `gc` / `export` / `explore` 全是孤儿
