### 3.2 Q2 / Q6 深度说明（科普）

#### Q2 答复：`bin: cli.js` 是什么

| 维度 | 当前 `bin: oxn` (binary) | 改 `bin: cli.js` (JS 入口) |
|---|---|---|
| 物理 | `dist/oxn` 63 MB | `dist/cli.js` ~500 KB |
| runtime | 0（自带 Bun runtime） | 用户机需装 Bun ≥ 1.1 |
| 启动 | `< 30ms`（无 runtime 加载） | `~50ms`（Bun） |
| 跨平台 | ❌ 单 OS（macOS arm64） | ✅ 跨 3 OS |
| npm 包体积 | 63 MB | < 1 MB（**-98%**） |
| 用户下载成本 | 高（200MB+ for 3 OS） | 低（< 1MB） |
| CI build | 3 OS × 1 min = 3 min | 1 OS × 10s = 10s |
| 升级 | 重新下 binary | 增量更新 JS |

**npm 自动处理**：
- 读 `package.json:bin` → 在 `node_modules/.bin/oxn` 建 symlink
- 自动加 shebang `#!/usr/bin/env node`（或 bun 取决于 engines）
- `oxn --version` 直接跑

#### Q6 答复：npm 发布机制 vs Bun 编译 vs 现代 CLI 工具

**npm 发布全流程**：
```
1. npm login
2. 改 package.json (name, version, files, bin, engines, publishConfig)
3. npm publish --dry-run    # 模拟
4. npm publish              # 实际：打包 tarball → 传 npm registry
5. 用户 npm install <pkg>    # 解包到 node_modules/
6. npm 自动：读 bin/main/types → symlink + 解析
```

**四种 CLI 工具发布模式对比**（2026 流行）：

| 工具 | 运行时 | 包大小 | 启动 | 跨平台 | 入口策略 |
|---|---|---|---|---|---|
| **OpenXenon**（本项目） | Bun | 计划 < 1MB | ~50ms | ✅ | `./dist/cli.js` |
| **OpenCode** | Bun | ~50MB | < 100ms | ✅ | Bun 单 binary + OS-specific |
| **OpenSpec** | Node | ~5MB | ~200ms | ✅ | 纯 JS + `engines.node` |
| **Rust 工具链**（ripgrep, fd, bat） | 0 | ~5MB | < 30ms | ✅ | 编译 binary per OS/arch |

**OpenXenon 选 JS 入口 + Bun runtime 最合适**：

1. 已是 Bun 项目（`bun.lock`），要求 Bun 零额外负担
2. 用户群是工程师（已有 Bun 或 Node 18+）
3. CI 已有 Bun 工具链（无需 N×M 编译矩阵）
4. 体积小、发布快、跨平台 0 成本

## 5. Prepublish 钩子设计

### 5.1 当前 `prepublishOnly`（不完整）

```json
{
  "prepublishOnly": "bun run build"
}
```

只跑 build，没跑测 + typecheck + lint。

### 5.2 v0.1.0 `prepublish`（完整）

> **修订**（阻断性问题 #1 修复）：
> 1. `engines` 字段改为 `node >=18.0.0`（Q8=a 拍板）
> 2. `build:dist` 命令改为 `--target=node`（**关键**）—— 产物必须在 Node 18+ 下能跑
> 3. bun build 仍可工作（`--target=node` 是 Bun build 的合法 target）

```jsonc
{
  "scripts": {
    "prepublish": "bun run prepublish:check && bun run prepublish:build",
    "prepublish:check": "bun run typecheck && bun run lint && bun test",
    "prepublish:build": "bun run langium:generate && bun run build:clean && bun run build:dist && bun run build:types",

    "build:clean": "rm -rf dist",
    "build:dist": "bun build ./src/cli/index.ts --target=node --outfile dist/cli.js",
    //                                                                          ^^^^^ 修订：bunn → node
    "build:types": "tsc --emitDeclarationOnly --outDir dist/types",

    "build": "bun run prepublish:build"  // 兼容 alias
  },
  "engines": {
    "node": ">=18.0.0"
  }
}
```

**前置条件**：Step 0 runtime 适配层**必须**已完成（[`runtime-adapter-design.md`](./2026-06-11-runtime-adapter-design.md)），否则 `dist/cli.js` 在 Node 下会因 `Bun.spawn` 未定义崩溃。

### 5.3 `prepublish` vs `prepublishOnly` 区别

| 字段 | 时机 | 用途 |
|---|---|---|
| `prepublish` | `npm publish` + `npm pack` 都跑 | 灵活 |
| `prepublishOnly` | 仅 `npm publish` 跑 | 严格 |

**推荐 `prepublishOnly`**（仅 publish 时跑，避免 `npm pack` 等也跑全测）。

### 5.4 build 产物预期

| 路径 | 大小 | 内容 |
|---|---|---|
| `dist/cli.js` | ~500 KB | CLI 入口（target=bun） |
| `dist/types/index.d.ts` | ~100 KB | TS 类型 |
| `dist/types/...` | ~1 MB | 全套类型 |

**总 < 2 MB**（vs 当前 63 MB binary，**-97%**）

## 8. npm 跨平台 vs Bun 编译 vs 现代 CLI 工具对比

### 8.1 三种发布模式

| 模式 | 代表 | 优势 | 劣势 |
|---|---|---|---|
| **A. JS 入口 + 跨平台 runtime** | OpenSpec, Vite, esbuild | 包小、跨平台、CI 快 | 需用户装 runtime |
| **B. Bun/Node SEA + 单 binary** | OpenCode (推测), Rust 工具链 | 0 依赖、最快启动 | 大、需 N OS × N arch 编译 |
| **C. Go/Rust 编译 binary** | ripgrep, fd, bat | 0 依赖、最快 | 需 Go/Rust 工具链 |

### 8.2 OpenCode / OpenSpec 实际策略

| 项目 | 仓库 | runtime | 包策略 | 入口 |
|---|---|---|---|---|
| **OpenCode** | `github.com/sst/opencode` | Bun | 多 OS binary + tarball | per-OS shim |
| **OpenSpec** | `github.com/Fission-AI/OpenSpec` | Node 18+ | 纯 JS + `engines.node` | `dist/cli.js` |
| **OpenXenon**（本项目） | `github.com/openxenon/openxenon` | Bun ≥ 1.1 | 纯 JS + `engines.bun`（推荐） | `dist/cli.js` |

**结论**：OpenXenon 选 OpenSpec 模式（纯 JS + runtime）最匹配项目实际。

## 9. bin: cli.js 与 bin: oxn 对比

### 9.1 4 种 bin 方案

| 方案 | bin | 体积 | 跨平台 | 启动 | 依赖 |
|---|---|---|---|---|---|
| **A** 现行 | `./dist/oxn` (binary) | 63 MB × 3 OS = 189 MB | ❌ 仅当前 OS | < 30ms | 0 |
| **B** 改 JS 入口（**Q6=a**） | `./dist/cli.js` | ~500 KB | ✅ 跨平台 | ~50ms | 用户装 Bun |
| **B'** 改 JS 入口 + **Node 兜底**（**Q8=a 修订**） | `./dist/cli.js` | ~500 KB | ✅ 跨平台 | ~50ms（Bun）/ ~200ms（Node） | **Node 18+ 已内置**（用户零依赖） |
| **C** 双 bin | `oxn` (binary) + `oxn-js` (JS) | 189 MB + 500 KB | ✅ | 选 | 0 / 用户 |
| **D** 仅 Node | `./dist/cli.js` + `engines.node: ">=18"` | 500 KB | ✅ | ~200ms | 用户装 Node |

### 9.2 选 B' 理由（**Q6=a + Q8=a 联合**）

1. **OpenXenon 已是 Bun 项目**（`bun.lock`），开发期 Bun 提速
2. **npm 包体积**从 63MB 降到 < 1MB（**-98%**）
3. **跨平台零成本**（同份 JS 在 macOS/Linux/Windows 都跑）
4. **CI build 时间**从 3 OS × 1 min 降到 1 次 × 10s
5. **`engines.node >=18`**：用户零依赖（Node 几乎人人有）
6. **双 runtime 路径**（Bun 加速 + Node 兜底）：自动 detect，**用户无需配置**
7. **现代 CLI 趋势**（TypeScript / vite / zod / citty / execa 同款）

**前置依赖**（Q9=a）：runtime 适配层（详见 [`runtime-adapter-design.md`](./2026-06-11-runtime-adapter-design.md)），5 模块 + 14 handler 改造。

### 9.3 npm 自动处理 bin 流程

```bash
# 用户安装（Node 18+ 兜底，零额外依赖）
npm install -g openxenon@0.1.0
# → 自动建 symlink: node_modules/.bin/oxn → ../openxenon/dist/cli.js
# → 全局可用: oxn --version（自动加 shebang #!/usr/bin/env node）

# 用户若有 Bun（可选加速）
bun --bun oxn --version  # 启动 50ms（vs Node 200ms）
```

### 9.4 用户安装命令（README 双 install）

```bash
# 主流：npm
npm install -g openxenon@0.1.0

# 现代：pnpm
pnpm add -g openxenon@0.1.0

# 加速（可选）：Bun
bun install -g openxenon@0.1.0

# 任意 OS / 任意包管理器都能装；runtime 由 detectBun() 自动选
```

**build target 影响**（审查修订）：
- `build:dist` 命令：`bun build ./src/cli/index.ts --target=node --outfile dist/cli.js`
- 产物是 Node 18+ 兼容的 ESM JS，**无 Bun runtime 依赖**
- 开发期仍用 Bun（启动快、typecheck 准），但产物不锁 Bun
- 若用户已装 Bun，`globalThis.Bun` 存在 → 适配层自动走 Bun 路径（spawn/file/glob 都用 Bun API 加速）
- 若用户未装 Bun，Node 18+ 全局 fetch 等覆盖 → 适配层自动走 Node 路径

## 10. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| i18n en-US 翻译质量低 | 中 | 海外用户看不懂错误 | 用 LLM 翻译 + 中文语境标注 + 关键错误双语 fallback |

| 文档同步漏（README 与代码漂移） | 中 | 用户困惑 | 写 `v0.1.0` 总结 forge 兜底 |

## 13. 决策记录（ADR）

### ADR-007：v0.1.0 = 第一版稳定发布，semver 严格执行

**决策**：v0.0.27 → v0.1.0 是开发期 → 稳定期切换点。后续 v0.1.x 严格 semver（patch 修 bug，minor 加 feature，major 破坏）。

**理由**：
- 1033 测试全绿 + grammar 修复 + T1/T2 测 = 稳定基础
- 0.0.x 标签下内部迭代已完成
- v0.1.0 是公开 API 承诺起点

**含义**：
- v0.1.0 后的破坏性变更必须升 v0.2.0
- patch 兼容 0.1.0，minor 兼容 0.1.x
- v0.2.0 = Daemon / Hall 强化阶段

**决策者**：架构师 + 维护者

### ADR-008：bin 改为 `./dist/cli.js` + `engines.bun >=1.1`（Q6=a）

**决策**：放弃 63 MB Bun compiled binary，改用 < 1 MB JS 入口。

**理由**：
- 包体积 -98%
- 跨平台零成本（同份 JS）
- CI build 时间 -83%
- OpenXenon 已是 Bun 项目，要求 Bun 零额外负担

**替代方案**：
- B. 保留 63 MB binary + 3 OS build matrix — 体积大、CI 慢
- C. 双 bin（binary + JS）— 用户困惑
- D. 仅 Node — 与项目实际 runtime 不符

**决策者**：架构师 + 维护者 + 用户

### ADR-009：i18n v0.1.0 补 en-US + 扩 3-5 个命令（Q4=a / Q5=a）

**决策**：v0.1.0 必须有 en-US locale（npm 海外用户），且覆盖 init / config / work / proof 错误消息。

**理由**：

- 海外用户是潜在增长点

**含义**：

- 关键错误消息加 `t(...)` 调用

**决策者**：架构师 + 维护者

### ADR-012：Runtime 适配层 + 双 runtime 路径（Q8=a / Q9=a / Q11=a）

> **审查后修订**（阻断性问题 #1 修复）：runtime 适配层位置提升到 `src/infra/runtime/`（**根级别**），`build:dist` 改 `--target=node`。

**决策**：
1. 在 `src/infra/runtime/` 新增 5 个 runtime 适配模块（`detect.ts` / `spawn.ts` / `file.ts` / `glob.ts` / `which.ts`）
2. 将 14 处 Bun API 用法抽象到适配层
3. **`engines` 改为 `node >=18.0.0`**（不再要求 Bun）
4. **`build:dist` 改 `--target=node`**（产物必须 Node 18+ 兼容）
5. 双 runtime 路径（Bun 加速 + Node 兜底）由 `detectBun()` 自动选

**理由**：
1. **推广便利**（核心）：Node 18+ 兜底让 npm install 0 负担（用户调研硬约束）
2. **不丢 Bun 优势**：用户装了 Bun 自动用 Bun 路径（启动 50ms vs 200ms）
3. **架构一致**：L1-Infra 内部新增，零层间违规
4. **回归保护**：双 runtime 测矩阵确保两路径行为一致
5. **未来扩展**：Deno / Workers / etc. 也能复用适配层
6. **TypeScript-Vite 风格**（Q11=a）：ESM 优先 / 构建与类型分离 / 拥抱现代 Web API / 插件式 / 零 runtime 强依赖 / 跨平台 / 体积小

**审查修订**：
- 适配层从 `probes/runtime/` 提升到 `infra/runtime/`（审查阻断 #2 修复）
- `which` 改用 npm `which` 包（审查阻断 #4 修复）
- `detectBun()` 模块加载时缓存（审查中等 #5 修复）
- `spawn` 强制缓冲 stdout/stderr（审查中等 #6 修复）
- CI Node 矩阵改用 `node dist/cli.js` 端到端验证（审查阻断 #3 修复）

**含义**：
- 5 个 runtime 模块 + 14 处 probe handler 改造 + 22 个新测
- v0.1.0 总测数：1033 + 22（T1/T2）+ 22（runtime 适配）= 1077
- `engines: { node: ">=18.0.0" }`（不再要求 Bun）
- 适配层详见 [`2026-06-11-runtime-adapter-design.md`](./2026-06-11-runtime-adapter-design.md)

**替代方案**：
- A. 全部走 Bun（engines.bun）—— 用户不愿装 Bun，推广劣势
- B. 全部走 Node —— 失去 Bun 启动速度优势
- C. 编译 binary（63MB）—— 体积大、CI 慢、跨平台难
- D. brew/scoop（OpenCode 模式）—— 仍需 brew，仍有用户门槛
- **E. 适配层（双 runtime）** —— **✅ 选**——Node 兜底 + Bun 加速，零用户负担

**决策者**：架构师 + 维护者 + 用户（Q8=a / Q9=a / Q11=a）
