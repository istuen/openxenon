**§1 Work 的 9 阶段生命周期**



**§1.1 一句话定义**


Work 是 OXN 中"从 Intent 到 Proof"的一次完整编排。一份 `work.oxn` 从创建到归档，沿 8 阶段流程推进；每阶段有明确的文件产物与准入 / 拒绝条件。`oxn init` 作为项目级阶段 0 独立于 `oxn work` 子命令树。

**§1.4 Round 循环（v0.6 PR-2）**


`WorkspaceState.roundHistory: RoundRecord[]` + `currentRound: number`（dual-state.ts:65-66）。RoundRecord: `{ round, startedAt, endedAt, verdict ∈ {PASSED, FAILED, INCONCLUSIVE, PENDING}, failures: task 名列表, notes? }`。Round 1 默认 `verdict:'PENDING'` 在 `createInitialWorkspaceState`（dual-state.ts:128-135）。

**§2.4 Mode 设计（5 workType → 3 first-class mode + 旁路）**


```
CLI 字符串 (5 个 workType)
    │
    ├── 'task' / 'explore' / 'edit' ──→ workTypeToMode( ) ──→ WorkModeSchema (3 enum)
    │                                                            ↓
    │                                                       BirthCert.mode
    │
    ├── 'workspace' / 未知字符串 ──→ 兜底 mode='task' + warning
    │
    └── 'asset' ──→ handleAssetModeCreate( ) 旁路
                     ├─ 不调 workTypeToMode
                     ├─ 不写 .work / .run
                     ├─ 不进 task DAG
                     └─ 写 .openxenon/assets/{kind}/{name}.oxn
```

**真理源与转换函数**：

| 角色 | 文件 | 行 |
|---|---|---|
| ① Zod enum 真理源 | `packages/engine/src/Work/birth-cert.ts` | **35** `WorkModeSchema = z.enum(['task','explore','edit'])` |
| ② workType→mode 转换 | `packages/engine/src/Work/work-validator.ts` | **25-30** `workTypeToMode()` |
| ③ CLI 双分支 dispatcher | `packages/cli/src/commands/work.ts` | **400-449** `handleAssetModeCreate` + **501-509** 互斥 dispatch |
| ④ 业务词汇 SSOT | `.openxenon/assets/domains/WorkOrchestrationContext.oxn` | `term WorkType` / `term WorkMode` / `invariant` |
| ⑤ 测试守住 | `packages/engine/src/Work/__tests__/work-orchestration-context.test.ts` | **30-130**（9 case 锁定） |

**关键设计**：
- **3+2 三段式**：3 个 first-class mode（schema 严格验证）+ 2 个 CLI 字符串特殊路径（`workspace` 降级；`asset` 旁路）。
- **BirthCert.mode 字段恒为 3 选 1**：写入前先经 `workTypeToMode` 归一化，schema 强制验证。
- **`explore` / `edit` 实质等同 `task`**：Mode 仅在 BirthCert.mode + CLI 输出 + warning 文本中体现差异化；运行时共享 `dual-state-exec.runWork`。
- **edit 模式二级字段**：`editTarget` ∈ `domain:X | blueprint:Y`（`birth-cert.ts:44-49` EditTargetSchema），仅 mode='edit' 时填，其余 mode 留 null。


**§2.5 关键设计模式归纳**


1. **Zod schema 在 dual-state.ts 单点真理**；所有 .run/state.json 路径走 `loadWorkState` / `saveWorkState` 路径固化。
2. **BirthCert（.work 静态卡）** 是唯一可执行前的"准入证"；`applyPlanLock` 在 lock 时一次性写入 hash。
3. **原子写约束**：所有 state / frozen 写入都是 `writeFileSync(tmp) + renameSync()`（POSIX atomic），见 dual-state-io.ts:122-125, 196-199。
4. **双层状态机**：work.oxn 级（WorkspaceState）+ task.oxn 级（TaskState），通过 `workName` 关联；状态推进时双向同步 updatedAt。
5. **CLI 单文件 dispatcher**：所有 22 subcommand 在 work.ts 中各占一段，**无子目录拆分**——这是技术债候选（3389 行）。
6. **Asset 旁路是反向桥**：`handleAssetModeCreate` 早返回（work.ts:501-509），让 `oxn work --type asset` 表面是 work 但实际走 Asset DDD 模块。
7. **CLI 自实现 lock**（work.ts:2355 inline applyPlanLock + readBirthCert），绕过了 work-lock.ts 的 lockWork/unlockWork 公开函数——work-lock.ts 是 `lockWork/unlockWork` 两函数的 dead module。

> 本节采用多路径表呈现；review 期拍板。


**§8.1 D1. finalize 何时写 work-level `.run/frozen.json`？**


| 选项 | 行为 | 利 | 弊 |
|---|---|---|---|
| (a) 一律覆盖写 | finalize 不论 verdict 都写/覆盖 | 实现简单 | 若之前 submit 已写 PASSED，会被 finalize 抹掉 |
| (b) 兜底写 | 仅当 `.run/frozen.json` 不存在时写 | 不破坏 submit 路径 | finalize 必须兜底，可能掩盖 submit bug |
| (c) 全部 PASSED 才写 | 失败路径不写 work frozen，只写 task frozen | 与语义对齐 | 失败工作无完整 frozen 归档 |
| **(d) 提案** | 复用 `finalizeWorkDomains` 的"二阶段原子写"，draft → rename → chmod 0o444；保留 PASSED/FAILED/INCONCLUSIVE 三态；与 T12 完全对齐 | 与 T12 一致；audit-grade | 实现多 80 行 |


**§8.2 D2. finalizeWorkDomains 失败 verdict 时是否把 work 标 failed？**


| 选项 | 行为 |
|---|---|
| (a) 是，闭合失败路径 | finalize 调 finalizeWorkDomains；如存在 domainProof 含 FAIL，work 标 failed 且抛 `OXN_FINALIZE_REJECTED` |
| (b) 否，仍允许"总结失败" | finalize 调 finalizeWorkDomains；verdict=FAILED 仅警告，work 状态由用户叙事 |
| **(c) 提案** | finalizeWorkDomains 在 draft 阶段抛错 / 抛 warn 双选项；CLI 把 verdict 透传给 finalizeWorkDomains，由其按 domainProof 决议——`work.status` 跟随 verdict |


**§8.3 D3. `--run-probes` 在 submit 里如何生效？**


| 选项 | 行为 |
|---|---|
| (a) 注入 `.run/tasks/<t>/frozen.json.probeResults` | 与 v0.2 T5 frozen schema 对齐：3-state verdict；不动 Proof 子系统 |
| (b) 触发独立 Proof 子系统 | 真正接通 Proof；但需要 invoke `executeProbe`（要拉 Probe Registry）|
| **(c) 提案** | 仅接入 `workPrecheck`（已实现 + 单测覆盖），把 verdict 透传到 task frozen.json；完整 Proof 缝合留 v0.7.2 RFC |

**§9 状态机变化（finalize 路径）**


```
[submit 全部 PASSED]
     │
     ▼
[submitTask 写 .run/tasks/<t>/frozen.json]
     │
     ▼
[submitTask 写 .run/frozen.json, work.status='passed']   ← 已有
     │
     ▼
[finalize]──┐
            ├─ finalizeWork( state, opts = {verdict, notes} ) ──┐
            │                                                    │
            │  ┌─ if hasDomainProofs ────────────────────────────┤
            │  │                                                   │
            │  │   finalizeWorkDomains({ workDir, verdict })      │
            │  │     ├─ PASSED   → chmod 0o444                    │
            │  │     │              state.status = passed         │
            │  │     ├─ FAILED   → state.status = failed          │
            │  │     │              + 抛 OXN_FINALIZE_REJECTED     │
            │  │     │              (符合 D2c 时)                  │
            │  │     ├─ INCONCLUSIVE → state.status = passed      │
            │  │     │              + trace warn                  │
            │  │     └─ UNSET     → state.status = passed         │
            │  │                                                  │
            │  ├─ always: writeWorkFrozen( workDir, state )       │
            │  │   ├─ 路径: .run/frozen.json (含 RoundRecord)     │
            │  │   ├─ 原子写: tmp+rename (POSIX)                  │
            │  │   └─ chmod 0o444 (PASSED) / 0o644 (FAIL/PENDING)│
            │  │                                                  │
            │  └─ state.json.status ← verdict                    │
            │                                                    │
            └─ trace event: finalize-work

[submit --run-probes]──┐
                        ├─ submitTask body 头部调 workPrecheck(state)
                        ├─ workPrecheck.probeVerdict ∈ {PASSED, FAILED,
                        │   INCONCLUSIVE, UNSET}
                        └─ probeVerdict 写进 .run/tasks/<t>/frozen.json
                            .probeResults[0]   （按 D3c）
```
