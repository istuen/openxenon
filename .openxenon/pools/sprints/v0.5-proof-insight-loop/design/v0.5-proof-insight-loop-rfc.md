# What

**v0.5 的核心命题**：构建从 Proof（证据）→ Insight（洞察）→ Intent（意图改进）的完整反馈闭环。

当前 OpenXenon 的 IAP 三轴（Intent → Align → Proof）是**单向流水线**：Domain/Blueprint 声明约束 → Work 实例化执行 → Proof 运行探针产出 frozen.json。但 Proof 的结果**不会反向驱动 Intent 的优化**——引擎能检测问题，却不能提出改进建议，更不能在审查后自动应用修改。

v0.5 填补这个缺口，4 个子 PR：

| PR | 名称 | 目标 | 周次 |
|----|------|------|------|
| **PR-A** | Proof Verdict .md | 每次 `oxn proof run` 产出人类可读的 `verdict.md` 结案文档 | W1 |
| **PR-B** | Insight cross-proof | `oxn insight --cross-proof` 跨多 proof 寻找趋势与关联规律 | W2 |
| **PR-C** | Insight pipeline | `oxn insight --pipeline` 从 Intent→Work→Proof 全程寻找有效性规律 | W3–W4 |
| **PR-D** | Intent review gate | `oxn pool review/approve` 审查改进建议后原子覆盖 Intent 资产 | W5–W6 |

**目标产物**：

- `oxn proof run` 产出 `verdict.md`（与 `frozen.json` 对等的不可变结案文档）
- `oxn insight --cross-proof` 扫描全部 proof 目录，输出跨证明趋势矩阵
- `oxn insight --pipeline` 关联 Domain/Blueprint/Work/Proof，输出 Intent 有效性报告
- `oxn pool review` / `oxn pool approve` 审查闸门 + 原子覆盖

# Why

## 1. 现状矛盾

### 1.1 Proof 只输出机器可读的 frozen.json

`oxn proof run` 当前产出 `frozen.json`（Zod schema，SHA-256 + chmod 0o444）。这是机器的 SSOT，但对人类不友好：

- 人类需要读 JSON 才能理解 proof 结论（verdict、per-probe 结果、interference flags）
- `oxn proof show` 的 `renderShowHuman()` 是终端一次性渲染，不落盘
- 不存在一份"看一眼就懂"的 proof 结案文档

**矛盾**：proof 的判决应该像法院判决书——既要机器可验证（frozen.json），也要人类可阅读（verdict.md）。

### 1.2 Insight 只能看单个 proof

`oxn insight <proof>` 当前模式是"单 proof + 累积 probe-stats.json"：
- 读入一个 frozen.json，结合 probe-stats 计算 emergent patterns
- 但 emergent patterns 的数据来源只有被动累积的 probe-stats（依赖每次 proof run 写入）
- **不能主动扫描**全部 proof 目录做跨 proof 分析
- **不能关联** Domain 声明、Work 执行过程与 Proof 结果的端到端规律

**矛盾**：引擎知道所有 proof 的历史数据（都在磁盘上），但 insight 命令只利用了被 probe-stats 压缩过的聚合数据。

### 1.3 Intent 改进没有审查闸门

Domain 和 Blueprint 是 IAP 的根源约束（SSOT），但当前修改它们：
- 通过 `$EDITOR` 直接编辑 `.oxn` 文件（无审查流程）
- `oxn domain create --force` 无条件覆盖
- 没有从 Proof 结果反向推导 Intent 改进的自动化链路
- 没有"建议 → 审查 → 应用"的闸门机制

**矛盾**：Domain 被设计为"业务硬规则"，但修改它比修改代码还随意。

### 1.4 反馈闭环缺失（核心架构缺口）

```
当前 IAP 流程（单向）：
  Domain/Blueprint ──→ Work ──→ Proof ──→ frozen.json
                                              │
                                         (断头路：结果无人消费)

期望 IAP 流程（闭环）：
  Domain/Blueprint ──→ Work ──→ Proof ──→ frozen.json + verdict.md
       ↑                                        │
       │                                        ▼
       │                                   Insight (cross-proof + pipeline)
       │                                        │
       │                                        ▼
       └────────────── 审查闸门 ←────── 改进建议 (audit pool)
```

## 2. 设计原则

**原则 1：MD 优先**。所有人类消费的输出（verdict、insight 报告、改进建议）均为 `.md` 格式，遵循 v0.3 MD-Native 语法规范。

**原则 2：不可篡改链**。verdict.md 与 frozen.json 对等不可变（chmod 0o444 + SHA-256）。改进建议的来源证据链可追溯（哪个 insight、哪些 emergent patterns、谁在何时审批）。

**原则 3：人不自动替代**。引擎提供检测和结构化建议数据，但最终是否修改 Intent 由人类（或 AI 代理）通过审查闸门决定。引擎不做自动覆盖。

**原则 4：L0 不做 IO**。所有跨文件扫描、关联分析、覆盖操作在 L1-Infra / L3-CLI 层完成。L0-Kernel 只提供纯函数算法（如跨 proof 数据合并、pipeline 有效性计算）。

# How

## PR-A: Proof Verdict .md 输出

### 目标

每次 `oxn proof run` 在产出 `frozen.json` 的同时，产出对等的人类可读 `verdict.md`。

### 文件位置

```
.openxenon/proofs/<proof-name>/
├── frozen.json          # 机器消费（已有）
└── verdict.md           # 人类消费（新增）
```

### verdict.md 格式

```markdown
---
proof_id: "<name>"
verdict: PASSED | FAILED | INCONCLUSIVE
run_at: "2026-06-25T10:30:00.000Z"
content_hash: "<sha256-of-body>"
frozen_hash: "<sha256-of-frozen.json>"
probe_count: 5
passed_count: 4
failed_count: 1
---

# Proof: <name>

> **Verdict**: ✅ PASSED (4/5 probes passed)
> **Run at**: 2026-06-25 10:30:00 UTC
> **Frozen**: `frozen.json` (SHA-256: `abc123...`)

## Evidence

- ✅ **ts-compiles** `src/cli/proof.ts`
  - fact: tsc --noEmit exited 0, 0 errors
  - conclusion: 满足验收

- ✅ **lint-check** `src/`
  - fact: biome check passed, 0 errors
  - conclusion: 满足验收

- ❌ **test-pass** `src/cli/__tests__/proof.test.ts`
  - fact: 3/4 tests passed, 1 failed
  - conclusion: 验收未通过：test "renderShowHuman INCONCLUSIVE" failed with assertion error

## Verdict Summary

| Metric | Value |
|--------|-------|
| Total probes | 5 |
| Passed | 4 |
| Failed | 1 |
| Inconclusive | 0 |
| Overall verdict | PASSED |

## Interference

_(none detected)_
```

### 实现要点

1. **复用 proof-compiler**：`src/oxl/md-bridge/compilers/proof-compiler.ts`（428 行，v0.3 已实现）提供 proof 的 MD 编译能力。PR-A 在 Proof CLI 的 `run` 命令末尾调用 `compileOxnToMd()` 或直接组装 MD。

2. **不可变性**：`verdict.md` 使用与 `frozen.json` 相同的 `writeFrozenImmutable()` 模式——chmod 0o444 + SHA-256 content_hash。`frozen_hash` 字段交叉引用 frozen.json 的 hash，确保两份文档的一致性。

3. **3 态 verdict 渲染**：复用 `renderShowHuman()` 的 3 态逻辑——PASSED → ✅（绿）、FAILED → ❌（红）、INCONCLUSIVE → ⚠️（黄）。

4. **L3 编排**：Proof CLI（`src/cli/proof.ts`）在 Phase 3（写 frozen.json 后）追加 Phase 3.5（写 verdict.md）。不改变现有 frozen.json 产出流程。

5. **verdict.md 与 frozen.json 关系**：
   - 同时产出，同时 0o444
   - `verdict.md` 的 `frozen_hash` 指向 `frozen.json` 的 SHA-256
   - `frozen.json` 的 `_xenon_meta` 可扩展 `verdict_md_hash` 字段做双向交叉引用（可选，PR-B 阶段评估必要性）
   - 若写 verdict.md 失败（磁盘满等），不影响 frozen.json 已写入——两者独立

### 影响范围

| 层 | 文件 | 变更 |
|----|------|------|
| L3-CLI | `src/cli/proof.ts` | `run` 命令追加 Phase 3.5 |
| L3-CLI | `src/cli/proof-frozen-writer.ts` | 新增 `writeVerdictMd()` |
| L3-CLI | `src/cli/__tests__/proof.test.ts` | 新增 verdict.md 格式 + 交叉引用测试 |
| L1-OXL | `src/oxl/md-bridge/compilers/proof-compiler.ts` | 可能微调以支持 CLI 直接调用 |

### 测试策略

- verdict.md 格式符合 heading skeleton（`## Evidence`、`## Verdict Summary`、`## Interference`）
- PASSED / FAILED / INCONCLUSIVE 三种 verdict 的正确渲染
- verdict.md 与 frozen.json 的 SHA-256 交叉引用一致性
- verdict.md 写入失败不回滚 frozen.json（独立产出）
- 并发写两个 proof 的 verdict.md 不互相影响

## PR-B: Insight cross-proof 模式

### 目标

`oxn insight --cross-proof` 主动扫描全部 `.openxenon/proofs/*/frozen.json`，寻找跨多个 proof 的趋势与关联规律。

### 与现有 `oxn insight <proof>` 的区别

| 维度 | 现有模式（单 proof） | 新增模式（cross-proof） |
|------|---------------------|------------------------|
| 数据源 | 1 个 frozen.json + probe-stats.json | proofs/*/frozen.json 全集 |
| 分析范围 | 本次 proof 的 evidence + stats 聚合 | 跨 proof 的趋势、关联、恶化/改善信号 |
| 输出 | evidence chain + probe stats + emergent patterns | 跨 proof 趋势矩阵 + 关联热图 + 恶化/改善信号 |
| 适用场景 | 单次 proof 结果解读 | 项目质量长期趋势分析 |

### CLI 接口

```bash
# 跨 proof 分析（默认扫描全部 proof）
oxn insight --cross-proof

# 限定 proof 范围
oxn insight --cross-proof --since 2026-06-01
oxn insight --cross-proof --proofs "proof-a,proof-b,proof-c"

# 按 probe type 过滤
oxn insight --cross-proof --probe-type ts-compiles,test-pass

# 输出格式
oxn insight --cross-proof --json   # JSON 输出（AI 消费）
oxn insight --cross-proof          # 默认 human 渲染（终端）
oxn insight --cross-proof --md     # 输出 cross-proof-insight.md 落盘
```

### 分析维度

#### 维度 1：Target 趋势矩阵

按 `(probeType, target)` 分组，展示每个组合在时间轴上的 verdict 变化：

```
Target Trend Matrix:
┌─────────────────────┬────────┬────────┬────────┬────────┬──────────┐
│ Target              │ run-1  │ run-2  │ run-3  │ run-4  │ Trend    │
├─────────────────────┼────────┼────────┼────────┼────────┼──────────┤
│ ts-compiles → cli/  │ PASS   │ PASS   │ FAIL   │ FAIL   │ ↓ worsening │
│ lint-check → src/   │ PASS   │ PASS   │ PASS   │ PASS   │ → stable    │
│ test-pass → infra/  │ FAIL   │ PASS   │ PASS   │ PASS   │ ↑ improving │
└─────────────────────┴────────┴────────┴────────┴────────┴──────────┘
```

#### 维度 2：Proof 关联热图

跨 proof 的探针类型共现关系——哪些探针经常在同一 proof 中一起失败：

```
Proof Correlation:
  ts-compiles ──┐
                ├── 80% 同时失败（"类型错误常伴随 lint 错误"）
  lint-check  ──┘
  test-pass   ──── 30% 与 ts-compiles 同时失败
```

#### 维度 3：恶化/改善信号

检测每个 target 的 verdict 序列（按时间排序），识别统计学显著的恶化或改善趋势：

- **连续恶化**：最近 N 次 proof 中 verdict 从 PASS → FAIL，且无恢复
- **连续改善**：最近 N 次 proof 中 verdict 从 FAIL → PASS，且保持
- **波动**：PASS/FAIL 交替出现，无明确趋势

#### 维度 4：Probe 有效性排名

按"实际触发 FAIL 的频率"对 probe type 排名：

```
Probe Effectiveness:
  1. test-pass      82% fail rate (triggered in 9/11 proofs)
  2. ts-compiles    64% fail rate (triggered in 7/11 proofs)
  3. lint-check     18% fail rate (triggered in 2/11 proofs)
  4. deps-resolved   0% fail rate (never triggered)
```

### 实现要点

1. **L1-Infra 扫描器**：新建 `src/infra/insight/cross-proof-scanner.ts`——扫描 `proofs/` 目录下的全部 `frozen.json`，按时间排序后返回 `FrozenProof[]` 列表。

2. **L0-Kernel 算法**：新建 `src/kernel/verdicts/cross-proof-compute.ts`——纯函数，入参 `FrozenProof[]`，出参 `CrossProofInsight`（含趋势矩阵 + 关联热图 + 恶化/改善信号 + 有效性排名）。

3. **CLI 编排**：扩展现有 `src/cli/insight.ts`，新增 `--cross-proof` flag。L3 调用 L1 扫描 → L1 返回数据 → L3 调用 L0 compute → L3 输出。

4. **输出格式**：
   - `--json`：`CrossProofInsight` JSON（AI 消费）
   - 默认：终端 human 渲染（表格 + 趋势箭头）
   - `--md`：落盘 `.openxenon/pools/audit/cross-proof-insight-<timestamp>.md`

5. **性能考虑**：proof 数量可能很大（长期项目 >100 个）。实现中需考虑：
   - 分页扫描（`--limit 50`）
   - 缓存最近扫描结果（避免每次全量反序列化）
   - 时间复杂度 O(n × m) where n = proof 数, m = per-proof probe 数

### 影响范围

| 层 | 文件 | 变更 |
|----|------|------|
| L0-Kernel | `src/kernel/verdicts/cross-proof-compute.ts` | 新建：跨 proof 趋势算法 |
| L0-Schema | `src/kernel/schemas/cross-proof-insight-schema.ts` | 新建：CrossProofInsight Zod schema |
| L1-Infra | `src/infra/insight/cross-proof-scanner.ts` | 新建：proofs/ 目录扫描器 |
| L3-CLI | `src/cli/insight.ts` | 新增 `--cross-proof` flag |
| L1-OXL | `src/oxl/md-bridge/compilers/insight-compiler.ts` | 新建：Insight MD 编译器（复用 verdict.md 格式） |

### 测试策略

- 空 proofs 目录 → 空趋势矩阵
- 单 proof → 无跨 proof 关联（返回单点数据）
- 3 proof 序列：PASS→FAIL→FAIL → 检测到 worsening 信号
- 3 proof 序列：FAIL→PASS→PASS → 检测到 improving 信号
- 3 proof 序列：PASS→FAIL→PASS → 检测到 volatile 信号
- 大量 proof（>100）→ 分页 + 性能不退化
- `--since` / `--proofs` / `--probe-type` 过滤正确

## PR-C: Insight pipeline 模式（Intent → Work → Proof）

### 目标

`oxn insight --pipeline` 关联 Domain/Blueprint 声明（Intent）→ Work 执行过程（Align）→ Proof 结果（Proof），寻找跨 IAP 三轴的有效性规律。

### 核心分析能力

#### 能力 1：Invariant 命中率分析

对每个 Domain invariant，统计在关联 Work 的 Proof 中实际触发的频率：

```
Invariant Effectiveness:
┌──────────────────────────────────────┬────────┬──────────┬──────────┐
│ Invariant                            │ Work   │ Proof    │ Hit Rate │
├──────────────────────────────────────┼────────┼──────────┼──────────┤
│ C1: ESM 项目禁用 CJS require()       │ 8      │ 8        │ 25%      │
│ C2: 路径解析必须读 AGENTS.md         │ 8      │ 8        │ 0%       │
│ C4: ReDoS 防护                       │ 8      │ 8        │ 12%      │
│ C5: Shell 命令执行必须参数化         │ 8      │ 8        │ 0%       │
│ P1: HIGH/CRITICAL 不得合入 main      │ 8      │ 8        │ 38%      │
└──────────────────────────────────────┴────────┴──────────┴──────────┘

Signals:
  ⚠️ C2 + C5 命中率 0% → 可能是冗余约束或检测手段不足
  📊 P1 命中率最高 → 这是当前质量瓶颈
```

#### 能力 2：Blueprint Slot DAG 偏差分析

对比 Blueprint 声明的 DAG 与实际 Work trace 的执行情况：

```
Blueprint "dev-workflow" DAG Drift:

Declared DAG:            Actual Execution:
  build                     build  ✅ (always passes)
  ├─ develop                develop  ⚠️ (60% fail at lint-check)
  └─ test                   test  ✅ (80% pass)
       └─ verify             verify  ❌ (fan-in blocked by develop 失败)

Signals:
  ⚠️ "develop" slot 的 lint-check 门禁过严 — 60% 失败率
  → 建议：在 develop 内部分拆 lint-check 到更早的 slot
```

#### 能力 3：Intent 覆盖率缺口检测

对比所有 Blueprint 声明了哪些观察维度，与实际 proof 跑过的探针类型：

```
Intent Coverage Gap:

Blueprints declare these observe probes:
  deps-resolved, lint-check, ts-compiles, test-pass

Proofs actually run:
  ts-compiles (11 proofs), lint-check (8), test-pass (11), deps-resolved (3)

Gap: deps-resolved 只被 3/11 的 proof 实际执行
  → 检查 Blueprint 的 observe 配置是否被正确实例化到 Work
```

#### 能力 4：Work → Proof 全链追踪

以单个 Work 为线索，追踪其完整的 IAP 生命周期：

```bash
oxn insight --pipeline --work <work-name>
```

输出该 Work 的端到端追踪：
- Intent：引用了哪些 Domain/Blueprint，声明的约束是什么
- Align：trace.jsonl 中的状态机事件（PART_START/COMPLETE/PROBE_RESULT）
- Proof：关联的 proof frozen.json 结果
- Gap：哪些 Intent 约束未在 Proof 中验证

### 实现要点

1. **L1-Infra 关联引擎**：新建 `src/infra/insight/pipeline-analyzer.ts`——跨 subsystems 的数据关联引擎。
   - 输入：`domains/` + `blueprints/` (OXL/MD) + `works/` (trace.jsonl) + `proofs/` (frozen.json)
   - 关联逻辑：通过 `work.oxn` 中的 `domain`/`blueprint` ref 建立映射

2. **L0-Kernel 有效性算法**：新建 `src/kernel/verdicts/pipeline-compute.ts`——纯函数。
   - `computeInvariantHitRate()`：Domain invariant → 对应 proof probe → 命中次数 / 总次数
   - `computeDagDrift()`：Blueprint slot DAG → Work trace → 偏差矩阵
   - `computeCoverageGap()`：Blueprint observe probes → Proof actual probes → 缺口列表

3. **Work ↔ Proof 关联**：通过以下方式建立映射：
   - 直接关联：`oxn work finalize` 产出的 `work-domains-frozen.json` 明确引用了 Work
   - 间接关联：通过 proof 的 `snapshotWorkMd()`（v0.4 PR-B Q4-A）的 `work-hash.txt` 反查 Work
   - 名称约定：若 Work 名为 `<w>`，关联 proof 可能也名为 `<w>`（但不是强制的）

4. **输出格式**：
   - `--json`：`PipelineInsight` JSON
   - 默认：终端 human 渲染（表格 + 信号标注）
   - `--md`：落盘 `.openxenon/pools/audit/pipeline-insight-<timestamp>.md`

5. **Hall 集成**：pipeline insight 的输出可被 Hall 的 `scanIntentPools()` 读取并在 HTML dashboard 展示。

### 影响范围

| 层 | 文件 | 变更 |
|----|------|------|
| L0-Kernel | `src/kernel/verdicts/pipeline-compute.ts` | 新建：pipeline 有效性算法 |
| L0-Schema | `src/kernel/schemas/pipeline-insight-schema.ts` | 新建：PipelineInsight Zod schema |
| L1-Infra | `src/infra/insight/pipeline-analyzer.ts` | 新建：跨 subsystems 关联引擎 |
| L1-Infra | `src/infra/frozen/domain-proof-evaluator.ts` | 可能扩展：记录 invariant→proof 映射 |
| L3-CLI | `src/cli/insight.ts` | 新增 `--pipeline` / `--work` flag |
| L3-CLI | `src/hall/index.ts` | Hall 集成：pipeline insight 数据源 |

### 测试策略

- 空 domains + blueprints → pipeline 返回空映射
- 单 Domain + 单 Blueprint + 单 Work + 单 Proof → 全链追踪正确
- invariant 从未被触发 → 命中率 0%，标注"冗余约束"信号
- Blueprint slot observe 与实际 proof probe 不一致 → 检测覆盖率缺口
- Work 无关联 Proof → 标注"无证据"而非报错

## PR-D: Intent improvement review/approve gate

### 目标

构建从 Insight 发现到 Intent 修改的审查闸门：改进建议写入 audit pool → 人类/AI 审查 → 审批通过后原子覆盖 Domain/Blueprint 文件。

### 完整流程

```
                          Insight (cross-proof / pipeline)
                              │
                              ▼
              ┌──────────────────────────────┐
              │  生成改进建议                   │
              │  (CLI 从 Insight 输出提取       │
              │   结构化建议写入 audit pool)      │
              └──────────┬───────────────────┘
                         │
                         ▼
              ┌──────────────────────────────┐
              │  oxn pool create audit       │
              │    --from insight <proof>     │
              │    --target domain <name>     │
              │                              │
              │  → .openxenon/pools/audit/   │
              │    <slug>.md                  │
              │    + frozen.json sidecar      │
              └──────────┬───────────────────┘
                         │
                         ▼
              ┌──────────────────────────────┐
              │  oxn pool review <slug>      │
              │                              │
              │  人类/AI 审查改进建议：         │
              │  1. 阅读 .md 中的建议内容       │
              │  2. 评估风险与收益              │
              │  3. 决定 approve 或 reject     │
              └──────────┬───────────────────┘
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
    oxn pool approve <slug>    oxn pool reject <slug>
              │                     │
              ▼                     ▼
    原子覆盖 Intent 资产        归档到 journal pool
    + frozen.json 审计链        + reject reason
```

### CLI 接口

```bash
# 从 insight 输出生成改进建议
oxn insight --pipeline --json | oxn pool create audit \
  --from insight \
  --target domain CodeQualityContext \
  --title "新增 invariant: ts-compiles 零错误约束"

# 手动创建改进建议（不依赖 insight）
oxn pool create audit \
  --target blueprint dev-workflow \
  --title "调整 develop slot 门禁顺序"

# 审查建议
oxn pool review <slug>              # 终端渲染可读视图
oxn pool review <slug> --json       # JSON 输出（AI 消费）

# 审批通过 → 应用修改
oxn pool approve <slug>             # 原子覆盖目标 Intent 文件
oxn pool approve <slug> --dry-run   # 预览将做出的修改

# 拒绝
oxn pool reject <slug> --reason "..."   # 归档 + 记录拒绝原因
```

### 改进建议的 audit pool 条目格式

```markdown
---
pool: audit
slug: "add-ts-compiles-invariant-code-quality-context"
target: "domain"
target_name: "CodeQualityContext"
target_path: ".openxenon/domains/CodeQualityContext.oxn"
source_insight: "pipeline-insight-2026-06-25T103000"
source_patterns:
  - cross-proof-fail-clusters: ts-compiles → src/cli/proof.ts
suggested_at: "2026-06-25T10:30:00.000Z"
status: pending  # pending | approved | rejected
---

# 改进建议：新增 invariant "ts-compiles 零错误约束"

## What

在 Domain `CodeQualityContext` 中新增 invariant：每次修改后 ts-compiles 必须零错误通过。

## Why

Pipeline insight 发现：
- `ts-compiles` 跨 7/11 proof 触发失败（64% fail rate）
- `src/cli/proof.ts` 连续 3 次出现 cross-proof-fail-clusters
- Blueprint `dev-workflow` 的 `develop` slot 已有 ts-compiles 门禁，但该门禁仅在 develop slot 触发，不覆盖其他修改路径

## How

在 `CodeQualityContext.oxn` 的 `invariant` 块中新增：

```oxn
invariant {
  "C6: ts-compiles 零错误门禁 — 所有 .ts 文件修改后必须通过 tsc --noEmit，不得有类型错误残留"
}
```

## 影响评估

- **破坏性**：低（新增 invariant，不修改现有约束）
- **涉及文件**：`.openxenon/domains/CodeQualityContext.oxn`
- **对已有 Work 的影响**：新 invariant 仅在新 `work finalize` 时生效，已有 frozen 不受影响
```

### approve 操作的原子覆盖流程

```
oxn pool approve <slug>
  │
  ├─ 1. 加载 audit pool 条目的 frozen.json（验证内容未被篡改）
  ├─ 2. 提取 target (domain/blueprint)、target_name、How 中的修改内容
  ├─ 3. 定位目标文件：.openxenon/domains/<name>.oxn 或 .openxenon/blueprints/<name>.oxn
  ├─ 4. 应用修改（合并 invariant、调整 observe、新增 term/ban 等）
  │     - 若为新增 invariant：追加到现有 invariant 块
  │     - 若为修改 observe：定位 Blueprint slot 并更新
  │     - 若为新增 term/ban：追加到现有 term/ban 块
  ├─ 5. 写 draft 文件 → oxn domain validate（验证语法正确）
  ├─ 6. 原子 rename：draft → 正式文件（覆盖）
  ├─ 7. 更新 audit pool 条目：
  │     - status: pending → approved
  │     - approved_at: ISO timestamp
  │     - approved_by: operator identity
  │     - before_hash: 覆盖前文件的 SHA-256
  │     - after_hash: 覆盖后文件的 SHA-256
  └─ 8. 写入 journal pool：记录覆盖事件（journal/<slug>.md + frozen.json）
```

### reject 操作的归档流程

```
oxn pool reject <slug> --reason "..."
  │
  ├─ 1. 更新 audit pool 条目 status: pending → rejected
  ├─ 2. 写入 rejected_at + rejected_by + reject_reason
  └─ 3. 不修改 Intent 文件，不写入 journal（保留 audit 中的完整记录）
```

### 安全性设计

- **不可抵赖**：每次 approve/reject 都写入 frozen.json（SHA-256 + chmod 0o444）
- **可回滚**：journal pool 记录覆盖事件，保存旧文件的 SHA-256
- **防篡改**：review 命令会校验 audit pool 条目的 frozen.json hash，确保改进建议自创建后未被修改
- **冲突检测**：approve 时检查目标文件是否自改进建议创建后被修改（对比 before_hash），若冲突则拒绝并提示人工合并

### 测试策略

- audit pool 条目创建 + frozen.json 一致性
- approve 正常流程：修改成功应用到 Domain/Blueprint
- approve 冲突检测：目标文件在建议创建后被修改 → 拒绝
- approve --dry-run：预览修改内容但不实际覆盖
- reject 流程：status 更新 + 不修改 Intent 文件
- 覆盖前后 hash 正确记录
- journal 条目正确写入覆盖事件
- 并发 approve 两个指向同一 Intent 的建议 → 第二个检测到冲突

# 决策记录

| 决策 | 结论 |
|------|------|
| verdict.md vs frozen.json 哪个是 SSOT？ | frozen.json 保持机器 SSOT；verdict.md 是人类消费的"视图"，两者 SHA-256 交叉引用确保一致性 |
| cross-proof 分析是否复用现有 probe-stats.json？ | 不复用。cross-proof 模式主动扫描全部 frozen.json 获取原始数据，probe-stats 的聚合数据可能丢失细节（如 per-proof verdict 序列） |
| pipeline 分析中 Work ↔ Proof 如何关联？ | 首选 `work-hash.txt` 反查（v0.4 PR-B），次选名称约定，末选 `work-domains-frozen.json` 直接引用 |
| approve 操作是否支持 Blueprint 修改？ | 是。audit pool 条目的 `target` 字段支持 `domain` 和 `blueprint` 两种类型 |
| 是否支持 AI 自动 approve？ | 不支持。approve 必须有明确的审查行为（人类或 AI 代理显式调用 `oxn pool approve`），引擎不做自动覆盖 |
| 旧的 Domain/Blueprint 文件是否保留？ | 不保留物理备份。通过 journal pool 记录覆盖事件（before_hash + after_hash），可追溯但不做文件级备份 |
| PR 依赖策略 | PR-A → PR-B → PR-C → PR-D 串行。PR-B 不依赖 PR-A 代码但依赖 PR-A 的 verdict.md 格式稳定；PR-C 依赖 PR-B 的扫描器；PR-D 依赖 PR-C 的 pipeline insight 输出 |

# 范围之外

以下内容**明确排除**在 v0.5 范围：

1. **实时监控**。insight 不提供 daemon 持续监控模式——每次 insight 分析是 CLI 手动触发的快照。
2. **AI 自动修复**。引擎不自动修改代码以解决 proof 失败——只提供建议，不自动修代码。
3. **跨项目洞察**。insight 只分析当前项目的 `.openxenon/` 数据，不关联多个项目。
4. **Blueprint 自动生成**。不根据 insight 自动生成新 Blueprint——只建议修改已有 Intent 资产。
5. **时间序列预测**。不预测未来质量趋势（如"预计 5 次 proof 后 ts-compiles 将永久 PASS"）——只分析历史数据。
6. **Intent 版本管理**。不引入 Domain/Blueprint 的 git-like 版本分支——覆盖后的旧内容仅通过 journal pool 记录 hash。
