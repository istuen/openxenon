### 2.2 阶段 1 目标 — md-bridge 核心 ✅

**核心问题**：如何把 Intent 5 类资产（.md 文件）解析为 OpenXenon Kernel Schema？

**端到端链路**：

```
[Intent MD file]
    │  1. unified pipeline 启动
    │     • remark-parse (CommonMark + GFM)
    │     • remark-directive (:::intent 容器指令)
    │     • remark-frontmatter (YAML)
    ▼
[mdast AST]
    │  2. 5 E_MD_xxx 校验
    │     • E_MD_INVALID_SYNTAX
    │     • E_MD_MISSING_REQUIRED
    │     • E_MD_TYPE_MISMATCH
    │     • E_MD_REFERENCE_BROKEN_FATAL
    │     • E_MD_HASH_MISMATCH
    ▼
[Validated mdast]
    │  3. mdast-to-kernel 转换器
    │     • domain → DomainSchema (Zod)
    │     • blueprint → BlueprintSchema (Zod)
    │     • work → WorkSchema (Zod)
    │     • task → TaskSchema (Zod)
    │     • proof → ProofSchema (Zod)
    ▼
[Kernel Schema (Zod 验证后)]
    │  4. IAP 引擎消费
    ▼
[Work execution + Proof verdict]
```

### 2.3 阶段 2 目标 — .oxn ↔ .md 双轨制 ✅

**核心问题**：如何让 .oxn（v0.2.0 格式）与 .md（v0.3 格式）共存且不冲突？

**真值来源（v0.3 §11.2 锁定）**：

> **`.md` = 唯一写入入口**。`.oxn` 由 `.md` 自动编译生成，**禁止反向修改**。

**双轨期数据流**：

```
用户/AI 编辑 .md
    ↓
pre-commit hook（v0.4 实施，本期提供 API）:
    1. 检测 .md contentHash
    2. 读取 .oxn sourceHash（来自 .oxn 注释）
    3. 若 H_md ≠ H_oxn：
       a. 触发 .md → .oxn 编译
       b. 更新 .oxn + sourceHash
       c. 写 meta: regenerated-from-md
    4. 若 H_md = H_oxn：跳过
    ↓
CI 守卫：
    • 拒绝 .oxn 手工修改
    • 强制 .md 重新编译（hash mismatch）
    ↓
运行时：
    • Kernel 优先读 .oxn（v0.2.0 兼容）
    • v0.4+ 可切换优先读 .md
```

## 9. v0.3 关键命题（设计哲学）

### 9.1 SSOT 边界

> **SSOT 不在于格式，而在于控制权。**
>
> OpenXenon 控制了 Intent 5 类资产（domain/blueprint/work/task/proof）→ 信任的基石。
>
> 外部文档保持原状；Intent MD 通过 URL/相对路径外链引用。

**（详见 [`intent-ssot-boundary.md` v1.0 §0](./intent-ssot-boundary.md)）**

### 9.2 MD-SSOT 不等于全栈 MD 化

> **MD-SSOT 不是"所有文档 MD 化"，而是"Intent 唯一 MD 化"。**

| 范畴 | 处理 | 理由 |
|---|---|---|
| **Intent**（domain/blueprint/work/task/proof）| ✅ MD + mdast + 5 E_MD_xxx | OpenXenon 内部决策 |
| **外部文档**（forges/, research/, issue/）| 保持原状 | 项目/外部输入 |

### 9.3 双轨制真值来源

> **`.md` = 唯一写入入口**。`.oxn` 由 `.md` 自动编译生成，**禁止反向修改**。

### 9.4 5 类 E_MD_xxx 二级严重程度

| 错误 | 严重 | 触发 |
|---|---|---|
| `E_MD_INVALID_SYNTAX` | Fatal | mdast 解析失败 |
| `E_MD_MISSING_REQUIRED` | Fatal | 必填字段缺失 |
| `E_MD_TYPE_MISMATCH` | Fatal | 字段类型不符 |
| `E_MD_REFERENCE_BROKEN_FATAL` | Fatal | 内部 Intent 引用断链 |
| `E_MD_REFERENCE_BROKEN_WARN` | Warn | 外部 URL/路径失效 |
| `E_MD_HASH_MISMATCH` | Fatal | frozen.json hash 不一致 |

### 9.5 Kernel = "Lambda Vacuum"

> Kernel 不知 OXL / mdast 存在。
> Kernel 只看 `FrozenBlueprint` / `XenonMeta` 等纯数据结构（Zod 验证）。
> md-bridge 通过 adapter 模式（`mdast-to-kernel.ts`）桥接到 Kernel。

### 9.6 forges/ 永久保留

> forges/ 不再"物理删除"（v0.2 计划已废除）。
> 41 篇 v0.1.x / v0.2.x 历史过程产物作为**外部历史源**永久保留。
> OpenXenon 控制 Intent，外部项目控制外部文档——各自维护。

## 12. v0.3.0 改革扩展：MD-Native Grammar RFC（待实施）

> **状态**：🟡 **RFC 提案**（v1.0，2026-06-23）
> **基础**：[`md-native-grammar-rfc.md` v1.0](./md-native-grammar-rfc.md)
> **范围**：3 个串行子 PR（t18/t19/t20），~7 天
> **影响**：v0.3.0 发版前完成（breaking change：`:::intent{...}` 解析期抛 `E_MD_DEPRECATED_SYNTAX`）

### 12.1 改革动机

v0.3.0 阶段 1 引入 `:::intent{...}` 容器指令，但暴露 3 个**信息密度天花板**：

1. **编辑器 / AI 工具零支持** — GitHub / Obsidian / Typora / VitePress 全部不识别 `:::directive`
2. **复杂关系图谱无法无损表达** — Slot DAG、Task 嵌套 Part、Probe 结构化断言在 `:::intent` 形式下有损 10-40%
3. **AI 生成准确率低** — LLM 在多属性、引号转义上失败率 28-62%

### 12.2 改革方案（终版）

完全替换 `:::intent{...}` 为**纯原生 Markdown 层级映射**：

| 层级 | 含义 |
|---|---|
| `#` H1 | 顶层实体（`# Domain: Name`）|
| `##` H2 | 实体分类（`## Terms` / `## Bans` / `## Invariants`）|
| `###` H3 | 实例实体（`### Intent`）|
| 嵌套列表 | 子结构（`- part: build_module` 缩进）|

配合 **Factory + Singleton 架构**（`EntityRegistry` + 5 个 `EntityCompiler`）解耦 5 类实体。

### 12.3 关键决策（7 项）

| # | 决策 | 选定 |
|---|---|---|
| D1 | 语法范式 | A. 纯 MD（H 层级 + 嵌套列表）|
| D2 | 复杂属性表达风格 | A. 全嵌套列表（Task 下 Part 用 `- part:` 缩进）|
| D3 | ID 唯一性 | A. 强制 H3 文本在 `##` 分类内唯一 |
| D4 | 实体解耦模式 | A. Factory + Singleton（`EntityRegistry`）|
| D5 | PR 拆分粒度 | A. 3 个串行子 PR（grammar / migrate / highlight）|
| D6 | v0.3.0 发版策略 | A. v0.3.0 涵盖（发版前完成）|
| D7 | VitePress 站点改造 | A. 仅 CSS 着色（H2 分类加 border）|
