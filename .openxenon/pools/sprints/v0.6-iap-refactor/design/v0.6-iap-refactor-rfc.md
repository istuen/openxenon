# What — OXN 哲学模型

## 1. 四结构实体（E1-E4）

OXN 由 4 个**结构实体（Entity）**构建而成。这是**哲学理念层**，不直接映射代码目录或 L 层级：

```
┌──────────────────────────────────────────────────────────────────┐
│  E4 · Insight — 涌现层（1+1>2）                                    │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━                                       │
│  跨 Work 综合推理 → 资产级建议（新增/改进/废弃）                     │
│  哲学底色：钱学森系统论 · 整体论                                     │
│  不可还原 · 只能综合推理 · v0.6 哲学定位 + CLI 占位，v0.7+ 推理    │
└────────────────────────┬──────────────────────────────────────────┘
                         │ 综合集成
                         ▼
┌──────────────────────────────────────────────────────────────────┐
│  E3 · Engine — 引擎基座                                            │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━                                       │
│  整个 OpenXenon = Engine                                           │
│  独立验证主权（frozen.json + content_hash + planLock）              │
│  工程师体现实现在 L0-L2，L3 是工具入口                               │
└────────────────────────┬──────────────────────────────────────────┘
                         │ submit → 执行 IAP 循环
                         ▼
┌──────────────────────────────────────────────────────────────────┐
│  E2 · Work — 动态协作空间                                          │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━                                       │
│  Intent（工程师声明意图 + 选 Asset 边界）                           │
│  Align（AI 多轮对齐，Round × N → 每轮拆 M 个 Tasks）               │
│  Proof（Engine 独立验证 → verdict）                                │
│  Round：verdict fail → 回到 Intent 调整 → 新一轮 Align             │
│  工程师 ↔ AI 共建                                                  │
└────────────────────────┬──────────────────────────────────────────┘
                         │ ref 引用
                         ▼
┌──────────────────────────────────────────────────────────────────┐
│  E1 · Asset — 静态边界                                             │
│  ━━━━━━━━━━━━━━━━━━━━━━━━━━                                       │
│  Domain / Blueprint / Stack                                       │
│  硬约束（planLock + content_hash），不被 Work 改写                   │
│  工程师维护。形似 OpenSpec specs/，语义对立——被引用而非被改写        │
└──────────────────────────────────────────────────────────────────┘
```

**4 句定位**：

> **Asset 是边界**（工程师维护的硬约束，不被 Work 改写）。
> **Work 是协作**（IAP 三阶段多轮循环，工程师与 AI Agent 共建）。
> **Engine 是公证**（独立公证基座，**控制结构而非执行环境**，IAP 范式内核 + 适配层）。
> **Insight 是涌现**（1+1>2，**行为特征观测不评判代码质量**，钱学森系统论整体论，AI 跨 Work 综合推理）。

> **协作流水线 Slogan**（v1.3 拍板）：
>
> **工程师定意图，AI Agent 跑对齐，OXN Engine 出证明。**
>
> **终极命题**：工程师信任 AI Agent 在边界内的执行成果。

## 2. 工程实现模型（L0-L3）

E1-E4 结构在代码中通过 L0-L3 实现。L0-L3 是**工程分层的文档概念**，不直接对应物理目录——实际目录用各自名称（`kernel/`、`oxl/`、`infra/`、`Asset/`、`Intent/`、`Align/`、`Proof/`、`Insight/`、`cli/` 等）：

```
┌────────────────────────────────────────────────────────────────────────┐
│  L3: Tools & Applications (工具与应用层)                                │
│      - 面向用户/Agent 的直接交互界面                                     │
│      - 包含: CLI (oxn 入口), Skills (扩展能力), Daemon (后台强监督)       │
│      - E2 Work + E4 Insight 的入口编排在此层完成                          │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 驱动 / 调用
┌───────────────────────────────────▼────────────────────────────────────┐
│  L2: Engine Core Logic (引擎核心业务层)                                  │
│      - E1-E4 全部实现在此层（5 大业务模块 + IAP 状态机）                  │
│      - Asset / Intent / Align / Proof / Insight 各为独立业务模块         │
│      - 按 DDD 模块化组织：Service/<Domain>/{index,create,list,...}.ts   │
│      - 驱动 IAP 范式状态流转与可信证明的核心中枢                           │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 调度 / 依赖
┌───────────────────────────────────▼────────────────────────────────────┐
│  L1: Language DSL & Infra (操作基座与语言层)                             │
│      - OXL: OpenXenon Language 的 DSL 编译器/解析器                     │
│      - Infra: 文件/AST 扫描探针，为引擎提供 OS/硬件级操作基座            │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ 依赖 / 自举
┌───────────────────────────────────▼────────────────────────────────────┐
│  L0: Logic Kernel (逻辑内核层)                                           │
│      - 纯逻辑、无副作用的底层状态机与微型内核                              │
│      - 包含: 状态冻结机制（Freeze）、frozen.json 原子读写、Schema/Contract│
└────────────────────────────────────────────────────────────────────────┘
```

**关键边界**：
- **E1-E4 是哲学结构**（理念层），不直接映射代码目录
- **L0-L3 是工程分层**（概念层），描述代码的依赖方向，不直接对应物理目录
- **物理目录**直接用各自名称：`kernel/`、`oxl/`、`infra/`、`src/service/<Domain>/`、`cli/`、`daemon/`
- E1-E4 的**全部实现**都在 Engine（L0-L2），L3 是工具入口

## 3. Engine 内部职责映射

| E 实体 | L2 业务模块 | 核心能力 |
|---|---|---|
| E1 Asset | `service/Asset/` | Domain/Blueprint/Stack CRUD + sync + compile（硬约束边界维护）|
| E2 Work（Intent 阶段） | `service/Intent/` | 创建 Work + 选 Asset 边界 + 多轮调整 |
| E2 Work（Align 阶段） | `service/Align/` | AI 多轮对齐（Round）+ Tasks 执行 + 状态机 |
| E2 Work（Proof 阶段）| `service/Proof/` | 3 阶段探针执行协议 + frozen.json + verdict.md |
| E4 Insight | `service/Insight/` | 跨 Work 综合推理 + 资产级建议（涌现层）|
| 辅助 | `service/Pool/` | 5 类池 + review/approve/reject（资产改进闸门）|

## 4. Work = IAP 范式的最小完整单元

**v0.6 最重要的哲学收敛**：

```
任何工作 = 一次 work = IAP 周期的实例
  ├─ 创建 Domain？     →  Asset 模式 work（Intent=指定资产类型，Align=落盘，Proof=校验）
  ├─ 开发新功能？       →  Develop 模式 work（Intent=选边界，Align=Round 对齐写代码，Proof=跑探针）
  ├─ 跑一次验收？       →  Proof 模式 work（Intent=声明探针，Align=准备，Proof=跑探针写 frozen.json）
  └─ 做一次总结？       →  Insight 模式 work（Intent=定义维度，Align=扫描，Proof=产出报告）
```

**Skill 极简**：原来 3 个 Skill（oxn-cli / oxn-work / oxn-proof）→ **唯一 1 个 Skill `oxn-work`**

## 5. Work 内部 IAP 三阶段 + Round 多轮循环

Work 内部按 IAP 范式分 3 个 Work 模式（v0.6 从 4 个收敛为 3 个——Insight 升为 E4 涌现层）：

| 模式 | Intent 阶段 | Align 阶段 | Proof 阶段 | 典型用例 |
|---|---|---|---|---|
| **Asset 模式** | 创建 work，指定资产类型（domain/blueprint/stack） | AI 填写内容 + 落盘 | OXN 校验语法 + 写 planLock | 建 MemberContext Domain |
| **Develop 模式** | 选资产边界 + 定 goal + constraints | AI 写代码（Explore/Develop/Fix/Onboarding 4 子模式） | 跑 lint/test/build + verdict | 开发新功能 |
| **Proof 模式** | 声明探针集合 + 准备环境 | AI 执行准备 | OXN 跑探针 + 写 frozen.json | check-deploy 验收 |

**Round 机制**（v0.6 最小实现）：

```
Work (my-feature)
├── Round 1: intent + align + proof → verdict FAIL (type-check)
│   └── oxn work next-round → 回到 Intent 调整
├── Round 2: intent(adjust) + align + proof → verdict FAIL (lint)
│   └── oxn work next-round
├── Round 3: intent(refine) + align + proof → verdict PASS
└── finalize
```

**v0.6 最小实现**：
- Work 状态记录 `currentRound` 字段
- 新增 CLI 命令 `oxn work next-round <work>`——显式开启新一轮 IAP
- Verify fail 后**不自动循环**（避免无限循环），手动触发
- 每轮保留独立 `round-n/` 子目录（记录 intent/align/proof 快照）
- 全自动循环留 v0.7+

## 6. CLI 双路径设计

保留独立子命令作为快速通道，新增 `oxn work` 作为严谨路径：

```
oxn
├── init / config / install-skill           ← 工具型
│
├── domain / blueprint / stack             ← 资产层快速通道（保留，绕过 work）
├── proof                                   ← OXN 证明快速通道（保留）
├── insight                                 ← OXN 涌现通道（保留）
│
├── work                                    ← IAP 主入口（3 模式分发）
│   ├── create <w> --type asset|develop|proof

│   ├── run / submit / status / finalize / context
│   ├── next-round <w>                     ← v0.6 新增：开启新一轮 IAP
│   └── ...
│
└── token / probe / pool / dev              ← 保留
```

## 8. 代码架构：双包 Monorepo

**v0.6 物理目录从 `src/` 单包拆为 `packages/cli` + `packages/engine` 双包**：

```
openxenon (Monorepo)
├── packages/
│   ├── cli/                    ← L3 Tools 入口（薄组合调用层）
│   │   ├── src/commands/       ← 子命令（domain/blueprint/work/proof/insight/pool）
│   │   └── skills/             ← AI 技能集（静态资源注入）
│   │
│   └── engine/                 ← Engine 核心能力提供者
│       └── src/
│           ├── kernel/      ← 纯逻辑内核（Schema/Contract/Verdict/Processor）
│           ├── infra/   ← OXL DSL + Infra 探针基座
│           └──      ← IAP 业务逻辑（Asset/Intent/Align/Proof/Insight/Pool + daemon）
│
├── apps/hall/                  ← 未来 Web 研讨厅（v0.7+）
└── tests/                      ← 跨 package 集成测试
```

**关键设计**：
- **Daemon 在 Engine**：需要持续 IAP 循环（读写 L0 frozen.json + 调用 L2 Insight），不应放在 CLI
- **Skills 在 CLI**：作为静态资源在 build 时注入，不参与 Engine 运行时
- **CLI → Engine 单向依赖**：`import { create } from '@openxenon/engine/Asset'`

详见 [v0.6 Monorepo 设计稿](./v0.6-monorepo-packages.md)。

# Why — 旧 IAP 三轴的局限

## 1. 现状矛盾

### 1.1 旧 IAP 三轴叙事混淆"资产"和"流程"

旧叙事：
```
Intent 轴 ──→ Domain + Blueprint (由工程师创建，作为轴的产物)
Align  轴 ──→ Work + Task + Part
Proof  轴 ──→ Proof + Verdict
```

**问题**：Domain + Blueprint 实质是工程师沉淀的**可复用硬约束边界**，不应绑定在某个 IAP 轴上。把"资产"当作"Intent 轴的产物"掩盖了它"稳定约束"的本质。

### 1.2 Skill 数量过多

旧 3 个 Skill（oxn-cli / oxn-work / oxn-proof）让工程师被迫判断"这个工作属于哪个轴"再选 Skill。但实际上所有工作都可以建模为 work（IAP 周期）。Skill 的"分轴"是过度拆分。

### 1.3 物理目录命名与哲学脱节

旧 `.openxenon/{domains,blueprints,works,proofs}/` 按 IAP 轴分类，让"资产"看起来像"流程的副产品"。

### 1.4 旧 Insight 语义狭窄

v0.5 RFC 把 Insight 设计为"跨 proof 涌现模式"——读 frozen.json + probe-stats.json → emergent patterns。但实际更宏观的价值是"跨 Work 综合推理 + 资产级改进建议"。**Insight 应该是涌现层（E4），不是 Work 的子模式。**

## 2. 设计原则

**原则 1：E1-E4 哲学先行**。4 结构实体作为 OXN 的顶层概念，不直接映射代码目录。

**原则 2：L0-L3 单向依赖**。Tools (L3) → Engine (L2) → OXL+Infra (L1) → Kernel (L0)。

**原则 3：Work = IAP 最小单元**。所有工作都是 Work，Skill 只需 `oxn-work`。Round 是护城河（区别于 OpenSpec 的单次线性流程）。

**原则 4：Insight = 涌现层**。哲学上归属 E4（整体论），实现上归属 L2 Engine。v0.6 哲学定位 + CLI 占位，涌现推理留 v0.7+。

**原则 5：Asset = 硬约束边界**。区别于 OpenSpec 的"被改写的规范"——OXN Asset 有 planLock + content_hash 三层锁，被 Work 引用但不被改写。

## 3. 核心反转

| 维度 | 旧（v0.5） | 新（v0.6） |
|---|---|---|
| 核心隐喻 | IAP 三轴 | 4 结构实体（E1-E4）+ L0-L3 工程分层 |
| E1 Asset 定位 | Intent 轴的产物 | 工程师维护的硬约束边界 |
| E2 Work 定位 | Align 轴的执行空间 | IAP 周期承载体（含 Round 多轮循环） |
| E3 Engine 定位 | 分散的 Runtime 组件 | 独立验证主权基座 |
| E4 Insight 定位 | 跨 proof 涌现模式 | **涌现层**（钱学森系统论 1+1>2） |
| Skill 数量 | 3 个 | **1 个（oxn-work）** |
| 物理目录分类 | 按 IAP 轴 | 按"资产 vs 流程"分层（Config 软迁移） |
| Work 模式 | 4 个（含 Insight Mode） | **3 个**（Asset/Develop/Proof）+ E4 Insight 独立 |
| Round | 无 | **v0.6 最小实现**（currentRound + oxn work next-round） |

## v1.3 增量决策（2026-07-04 拍板，4 条 + 1 战略记录）

| 决策 | 结论 | 理由 |
|---|---|---|
| **主 Slogan 与叙事** | **"工程师定意图，AI Agent 跑对齐，OXN Engine 出证明"**；降级"三权分立/不可交叉/不可绕过"为主推词，保留为底层实现机制 | "三权分立"是政治隐喻，"不可绕过"是反 AI 的防御叙事；用户明确："工程师管工程，AI 工程落地，OXN 监督"是更可读、更易懂的协作流水线表达 |
| **Proof 角色定位** | **公证人，不是裁判**——`verdict` 字段是探针运行结果客观记录（脚本退出码、测试覆盖率、文件路径等），不评判"工作合格不合格"。"合格"判定属于工程师 | "OXN 说了不算，工程师说了算"是工具的边界；Engine 越权评判代码质量会侵蚀确定性 |
| **E4 Insight 作用域** | **行为特征观测，不评判代码质量**；用例命名 `probeEffectiveness` → `probeBehaviorPattern`（v0.6 PR-5d 实装） | "Insight 不评判代码质量"是讨论收敛的硬边界；行为特征（AI 用了哪些边界 / 触碰了什么 / Loop 收敛速度）才是工程师决策所需的信号 |
| **L0 Kernel 确定性** | **L0 Kernel 严禁引入概率性数学模型**（PID/ESN/突变论一律归属 Insight 模块） | Proof 之所以"硬"，是因为 Kernel 保持纯逻辑零副作用；任何概率性、模糊性、不确定性模型不得进入 Proof 决策路径 |
| **OpenXenon 理论定位** | **OpenXenon 是创作者对系统科学、AI Agent、软件工程三者结合的工程实践，不等同于系统科学，不代表系统科学** | 钱学森系统科学是底色与灵感，不是宣称；工具只证明有用，理论底蕴是底气而非枷锁 |
| **（战略记录）Agent 底座选型** | **Pi vs OpenCode 阶段 1 并行验证，决策不阻塞 v0.6.0 发版**；详见 [`agent-base-decision.md`](./agent-base-decision.md) | 战略问题不阻塞引擎发版；v0.6 只交付 Engine + CLI，Agent 选型是 v0.7+ 议题 |

## v0.7 RFC 主题预告（v1.3 锁定，4 大主题）

v0.6 是架构收敛版，v0.7 将开启"边界扩张 + 行为涌现"的发散期。以下 4 主题不阻塞 v0.6 发版，作为 v0.7 RFC 启动入口：

### 1. Memory 层（外部动态信息海关）

- **动机**：当前 Asset 是静态硬约束，缺少承接"依赖更新 / 外部文档 / Issue 动态"的中转层。耗散结构论要求开放系统持续吸收负熵流。
- **形态**：L1-Infra 旁路，`MemoryEntry { id, source, type, content, trust_score, related_asset_ids, related_roadmap_item, timestamp, ttl }`
- **与 Insight 关系**：Memory 是 Insight 的数据源之一（外部信号）
- **决策路径**：v0.7 RFC 主体；可选自研或引进 Mem0 / LangChain Memory
- **追踪**：见 [v0.7 RFC §Memory]（v0.7 RFC 待开）

### 2. Asset Roadmap（Asset 入口层）

- **动机**：当前 AI Agent 直接读 Asset 全部内容，Asset 多了之后 Token 浪费 + 注意力分散；harness-1.md §4 启发：Asset 的"剪枝"价值不在"记录"而在"约束"——Roadmap 是 Asset 对 AI 的剪枝接口
- **形态**：`Roadmap.md` 由工程师维护，作为 AI Agent 获取 Asset 的**唯一入口**；引用性内容（"任务 X 需读 Asset A 的 invariant C3"），**而非** Asset 全文
- **与 Memory 协同**：Roadmap 步骤可引用 Memory 中的动态信息条目
- **决策路径**：v0.7 RFC 主体

### 3. Insight 行为特征维度（E4 涌现层的"做什么"）

- **动机**：讨论明确 Insight 应是"行为特征观测"（AI 用了哪些边界 / 触碰了什么 / Loop 收敛速度 / 退出模式），而非代码质量度量
- **形态**：v0.6 PR-5d 已实装用例命名 `probeEffectiveness` → `probeBehaviorPattern`（强调行为特征而非 failRate 排序）；v0.7 引入新维度：
  - AI 触碰 Asset 规则频率（哪些规则被反复试探）
  - Loop 收敛特征（每轮 proof fail → 调整 → re-run 的次数与路径）
  - 退出模式（"AI 卡在某 Asset 上多久没有进展"）
- **数学模型归属**：PID/ESN/突变论等数学模型**仅在 Insight 模块内可选引入**，不得进入 Proof 决策路径
- **决策路径**：v0.7 RFC 主体

### 4. OpenXenon Agent 底座选型（Pi vs OpenCode）

- **动机**：harness-3.md 讨论提出 Pi Agent 更适合二次开发底座（极简、可控、可改造），但需阶段 1 并行验证
- **形态**：阶段 1 用 OpenCode 做"宽度验证" + Pi 做"深度验证"（Memory / Roadmap 概念验证）；阶段 2 评估选择；阶段 3 在选定底座上开发 `OpenXenon Agent`
- **决策路径**：战略记录 [`agent-base-decision.md`](./agent-base-decision.md) 已落档；v0.6.0 不阻塞，v0.7 启动
