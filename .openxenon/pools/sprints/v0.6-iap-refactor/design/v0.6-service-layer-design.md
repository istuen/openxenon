# What

## 1. 核心命题

**v0.6 把 CLI 从"含业务逻辑的厚壳"拆为"薄组合调用层"，把业务逻辑抽到独立的 Service 层**。

```
旧 (v0.5):
  packages/cli/src/commands/domain.ts (1237 行) ← 含 Domain CRUD 业务
  packages/cli/src/commands/blueprint.ts (1080 行) ← 含 Blueprint CRUD 业务
  packages/cli/src/commands/work.ts (3801 行) ← 含 Work 状态机业务
  packages/cli/src/commands/proof.ts (1112 行) ← 含 Proof 执行业务
  packages/cli/src/commands/insight.ts (513 行) ← 含 Insight 计算业务
  src/cli/pool-*.ts (5 文件) ← 含 Pool 审批业务

新 (v0.6):
  packages/engine/src/Asset/index.ts       ← Domain/Blueprint/Stack 业务 (DDD 模块化)
  packages/engine/src/Intent/index.ts      ← Work Intent 阶段业务
  packages/engine/src/Align/index.ts       ← Work Align 阶段业务
  packages/engine/src/Proof/index.ts       ← Proof 模式业务
  packages/engine/src/Insight/index.ts     ← Insight 3 模式业务
  packages/engine/src/Pool/index.ts        ← 5 池 + 审批闸门业务

  src/cli/                         ← 薄壳：parse args → 调 service → format output
```

**关键设计原则（DDD + 现代 JS/TS 模块化）**：
- Service = **模块**（目录），不是类
- 每个 Service 目录有 `index.ts` 统一入口
- 内部按用例拆分为多个文件（`create.ts` / `list.ts` / `compile.ts` / ...）
- 每个文件 `export` 一个 `async function`（无类、无状态）
- CLI 通过 `import { create } from '../service/Asset'` 或 `import * as Asset from '../service/Asset'` 调用

# Why

## 1. 现状问题（CLI 业务逻辑过重）

`src/cli/` 当前共 **63 个文件**，核心子命令文件含大量业务逻辑：

| CLI 文件 | 行数 | 业务函数 | 含 Service 内容 |
|---|---|---|---|
| `packages/cli/src/commands/work.ts` | **3801** | ~35 | work 状态机、validate/lock/run/submit/finalize/context |
| `packages/cli/src/commands/domain.ts` | **1237** | ~20 | Domain CRUD、validate、sync、compile |
| `packages/cli/src/commands/proof.ts` | **1112** | ~25 | Proof CRUD、3 阶段运行协议、frozen.json 写 |
| `packages/cli/src/commands/blueprint.ts` | **1080** | ~18 | Blueprint CRUD、validate、sync、compile |
| `packages/cli/src/commands/insight.ts` | **513** | ~12 | 单 proof / cross-proof / pipeline 3 种模式计算 |
| `src/cli/init.ts` | **350** | ~10 | 项目初始化 + AI Skill 注入 |
| 其他辅助 | ~6000 | ~50 | token / probe / pool / config / daemon |
| **合计** | **~14000** | **~170** | — |

**问题诊断**：
1. **CLI 文件过大**（work.ts 3801 行超维护阈值）
2. **业务逻辑与 IO 框架耦合**（业务函数直接 `console.log` / `process.exit` / `process.cwd`）
3. **不可测试**（无法 mock IO 测业务逻辑，必须跑真实文件系统）
4. **无法复用**（Daemon / Web UI 想调同一段业务逻辑只能 import CLI 函数）
5. **违反 L3-CLI 宪法**（CLI 层应只做编排，不写业务）

## 2. 设计原则

**原则 1：DDD 模块化**。Service 是目录（module），不是类（class）。每个目录有 `index.ts` 统一入口，内部按用例文件拆分。

**原则 2：纯函数式导出**。每个用例文件 `export async function create() {...}`，无类、无状态、无 DI 容器。CLI 通过 `import` 调用。

**原则 3：框架无关**。Service 不依赖 citty、不输出 console、不读 process.env。异常用 IAPError 表达，让调用方决定如何呈现。

**原则 4：可复用**。Service 可被 CLI / Daemon / Skill / Web UI / 测试任意调用，不被 CLI 独占。

**原则 5：可测试**。Service 调用 L1-Infra Port，测试时 mock Port 即可（无需真实文件系统）。

### 2.2 单文件模式（用例文件）

```typescript
// packages/engine/src/Asset/create.ts
import { IAPError } from '../../core/errors'
import type { CreateInput, CreateResult } from './types'
import { resolveAssetPath } from './internal/resolver'
import { renderAssetTemplate } from './internal/template'
import { FileSystemPort } from '../../infra/contracts/file-system-port'

/**
 * Asset Service — Create Use Case
 *
 * 创建一个新资产（Domain / Blueprint / Stack）的骨架文件。
 * - 写入路径由 config.assetRoot + config.assetDirs[kind] 解析
 * - 若 config 路径与 fallback 路径冲突，抛 IAP_ASSET_PATH_CONFLICT
 * - 文件已存在则抛 IAP_ASSET_ALREADY_EXISTS
 */
export async function create(input: CreateInput): Promise<CreateResult> {
  const fs = FileSystemPort.getInstance()                  // 注入（实际可走 DI 或全局）
  const assetPath = resolveAssetPath(input.kind, input.name, input.projectRoot)

  // 检查冲突
  if (await fs.exists(assetPath)) {
    throw new IAPError('IAP_ASSET_ALREADY_EXISTS', {
      kind: input.kind,
      name: input.name,
      path: assetPath,
    })
  }

  // 生成骨架内容
  const content = renderAssetTemplate(input.kind, input.name)

  // 写入
  await fs.mkdir(parentDir(assetPath), { recursive: true })
  await fs.writeFile(assetPath, content, 'utf-8')

  return {
    assetPath,
    content,
    createdAt: new Date().toISOString(),
  }
}
```

```typescript
// ✅ packages/engine/src/Asset/validate.ts（业务独立，纯函数）
import { IAPError } from '../../core/errors'
import type { ValidateInput, ValidateResult } from './types'
import { resolveAssetPath } from './internal/resolver'
import { FileSystemPort } from '../../infra/contracts/file-system-port'
import { createOxnParser } from '../../oxl/langium-driver/oxn-services'

export async function validate(input: ValidateInput): Promise<ValidateResult> {
  const fs = FileSystemPort.getInstance()
  const filePath = resolveAssetPath(input.kind, input.name, input.projectRoot)

  if (!await fs.exists(filePath)) {
    throw new IAPError('IAP_ASSET_NOT_FOUND', {
      kind: input.kind, name: input.name, path: filePath,
    })
  }

  const content = await fs.readFile(filePath, 'utf-8')
  const parser = createOxnParser()
  const r = await parser.parse(content, URI.file(filePath))

  if (r.parseErrors.length > 0 || r.lexerErrors.length > 0) {
    return {
      ok: false,
      errors: [
        ...r.parseErrors.map(e => `[Parser] ${e}`),
        ...r.lexerErrors.map(e => `[Lexer] ${e}`),
      ],
    }
  }

  const ast = r.ast as OXNDocument
  const domain = ast.entities.find(isDomainDeclaration) ?? null
  if (!domain) {
    return { ok: false, errors: ['no DomainDeclaration found in file'] }
  }

  return { ok: true, ast, domain }
}
```

## 8. 反模式（v0.6.0 之后禁止）

- ❌ 在 CLI 文件中写业务逻辑（应在 Service）
- ❌ 在 Service 中 `console.log` / `process.exit`（应抛 IAPError）
- ❌ 在 Service 中读 `process.env`（应通过 input 注入）
- ❌ Service 反向 import CLI
- ❌ Service 用 class + constructor injection（应纯函数式 export）
- ❌ 用 `Service/<Domain>/<Domain>Service.ts` 命名（应 `Service/<Domain>/index.ts` 统一入口）
- ❌ Service 暴露内部辅助函数（应在 `internal/` 子目录）

# 决策记录

| 决策 | 结论 | 理由 |
|---|---|---|
| Service 用类还是模块？ | **模块（DDD 风格）** | 用户要求：现代 JS/TS 模块化；`Service/<Domain>/index.ts` 统一入口 |
| Service 用 class 还是纯函数？ | **纯函数（`export async function`）** | 无状态、无 DI、易测试；CLI 只需 `import { create } from '...'` |
| Service 目录结构？ | **`Service/<Domain>/{index.ts, create.ts, list.ts, types.ts, internal/}`** | 用户示例：`Service/Asset/index.ts` 含 create/list/compile |
| Service 命名（PascalCase vs kebab-case）？ | **PascalCase**（`Asset/` 不是 `asset/`） | DDD 标准；区分文件夹 vs 文件 |
| delete 用例命名？ | **`delete.ts` 内 export `deleteAsset`**（避免关键字冲突） | `delete` 是 JS 关键字 |
| Service 异常表达？ | **`IAPError`**（已存在）+ 业务专属错误码 | 复用现有错误体系；Service 异常不混 console / process.exit |
| Service 可调用谁？ | **L1-Infra Port + L0-Kernel + L1-OXL** | 严格遵循 L 层级依赖；不得调 L3-CLI |
| Service 可被谁调用？ | **L3-CLI + Daemon + Web UI + 测试** | 任意调用方，CLI 不独占 |
| CLI 改造后行数？ | **~6200 行（从 ~14000 行减 56%）** | CLI 退化为薄壳 |
| 是否引入 DI 框架？ | **否**（Service 用 `FileSystemPort.getInstance()` 全局单例） | 避免引入 InversifyJS / tsyringe；保持轻量 |
| 是否引入新依赖？ | **否**（仍用现有 citty + Zod） | 避免引入新框架 |
| Service 拆分顺序？ | **Asset → Work → Proof → Insight/Pool** | 依赖顺序：Work 依赖 Asset 边界；Proof 依赖 Work run；Insight 依赖 Proof frozen |
| ESLint 新规则？ | **`packages/engine/src/**` 不得 import `src/cli/**`** | 强制架构边界；防止反向依赖 |

1. **Service 调用方扩展**（Web UI / gRPC / HTTP API）— v0.6 Service 接口为通用，但实际调用方只实装 CLI + Daemon + 测试
2. **Service 事件订阅**— v0.6 Service 是同步调用（return Promise），不暴露 EventEmitter
3. **Service 依赖注入容器**— v0.6 用全局单例（`FileSystemPort.getInstance()`），不引入 DI 框架
4. **Service 持久化层**— Service 不持有状态；每次调用从 L1-Infra 重新读 fs
5. **CLI 与 Service 的 IPC 拆分**— v0.6 仍是同进程；CLI 直接 import Service
