# 2. Core Concepts

## Blueprint

Blueprint is OpenXenon's "engineering drawing" - it defines the complete task structure.

### Blueprint Structure

```yaml
name: My Task
stages:
  - id: build
    name: Build
    proof:
      probes:
        - ref: shell_exec
          parameters:
            command: npm run build
  - id: test
    name: Test
    dependsOn: [build]
    proof:
      probes:
        - ref: shell_exec
          parameters:
            command: npm test
```

### Two Perspectives of Blueprint

- **For Engineers**: Human-readable YAML with task descriptions and stage definitions
- **For System**: Machine-parseable structured data for execution scheduling

## Arsenal

Arsenal is OpenXenon's "asset library" - it stores all standard assets.

### Asset Types

| Type | Description | Example |
|------|-------------|---------|
| **Probe** | Atomic check | `fs_exists`, `shell_exec` |
| **Proof** | Verification closure | Combines multiple Probes |
| **Stage** | Work node | `install-laravel`, `run-tests` |

## Stage

Stage is a "work node" in Blueprint, representing a phase of task execution.

### Stage Structure

```yaml
- id: build
  name: Build
  proof:
    probes:
      - ref: shell_exec
        parameters:
          command: npm run build
```

### Stage Execution Flow

1. AI gets task via `oxn task next`
2. Execute Stages in Blueprint order
3. Each Stage's Proof is evaluated by Kernel
4. Verification results recorded in task-trace.yaml

## Proof

Proof is a "verification closure" composed of one or more Probes.

### Proof Example

```yaml
name: laravel_install_proof
probes:
  - ref: fs_exists
    parameters:
      pattern: "vendor/laravel"
  - ref: fs_match
    parameters:
      path: "composer.json"
      pattern: "laravel/framework"
```

## DRAFT / CANONICAL Lifecycle

All Arsenal assets must go through a two-state lifecycle:

- **DRAFT**: AI generates via `oxn forge`, engineer reviews and promotes
- **CANONICAL**: Promoted via `oxn arsenal promote`, can be referenced by tasks

```
DRAFT ──[oxn arsenal promote]──▶ CANONICAL
```

## Task

Task is OpenXenon's task instance, bound to a Blueprint.

### Task Lifecycle

1. **CREATED** - Task created, Blueprint saved
2. **IN_PROGRESS** - Task executing
3. **PASSED** - All Stages and Proofs passed
4. **FAILED** - Some Proof failed

## Terminology

### System Roles

| Term | Definition |
|------|------------|
| **Engineer** | Provides high-level intent and constraints, doesn't write code directly |
| **AI Assistant** | Parses engineer intent, generates Blueprint and code |
| **oxn CLI** | Command entry, core functions work without Daemon |

### Core Concepts

| Term | Definition |
|------|------------|
| **Blueprint** | Complete task structure definition with multiple Stages |
| **Stage** | One execution phase of a task |
| **Proof** | Verification closure composed of one or more Probes |
| **Probe** | Atomic check (e.g., fs_exists, shell_exec) |
| **Arsenal** | Directory storing all standard assets |

### Lifecycle

| Term | Definition |
|------|------------|
| **DRAFT** | Asset draft generated by AI via `oxn forge` |
| **CANONICAL** | Officially reviewed asset that can be referenced by tasks |
| **task-trace.yaml** | Record file of task execution process |

## Concept Relationship Diagram

```
Blueprint
  ├── name (task name)
  └── stages (stage list)
        └── [Stage Name]
              └── proof
                    └── probes

Arsenal
  ├── probes/ (atomic checks)
  ├── proofs/ (verification closures)
  └── stages/ (work nodes)

Task
  ├── id
  ├── blueprint (references Blueprint)
  └── status (CREATED | IN_PROGRESS | PASSED | FAILED)
```
