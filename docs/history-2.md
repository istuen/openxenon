### 1、清单里的依赖关系（架构金字塔）
这 13 条原则不是平行的，它们构成了一个严格的层级依赖。**上层的原则必须依赖下层的原则才能成立。**
```text
┌─────────────────────────────────────────────────────────────┐
│ L3 运行时保证层 (时间维度的确定性)                            │
│  ├─ A7. 资产版本化 (冻结)                                   │
│  ├─ A9. Shadowing 可见性 (Meta注入)                          │
│  └─ A13. frozen.yaml Schema (终极形态)                       │
├─────────────────────────────────────────────────────────────┤
│ L2 动态组合层 (空间维度的灵活性，受严格约束)                   │
│  ├─ A5. Probe 追加语法 (append vs override)                  │
│  ├─ A6. Condition 静态裁剪                                  │
│  ├─ A8. Action 模板白名单 (禁止逻辑运算)                     │
│  └─ A3. ref + params_schema + 覆写机制                      │
├─────────────────────────────────────────────────────────────┤
│ L1 寻址复用层 (资产的可发现性与可达性)                        │
│  ├─ A2. Stage 升格 (一等公民)                               │
│  ├─ A4. 三层寻址 (oxn/@scope/./)                            │
│  └─ A12. Probe 命名空间                                     │
├─────────────────────────────────────────────────────────────┤
│ L0 实体模型层 (物理基石，不可动摇)                           │
│  ├─ A1. Task-Blueprint 1:1 锁死                             │
│  ├─ A10. Proof 不升格                                       │
│  └─ A11. Stage/Proof 合并 (平铺结构)                        │
└─────────────────────────────────────────────────────────────┘
```
**依赖逻辑：**
没有 L0 的平铺结构 (A11)，就不可能有 L1 的 Stage 独立寻址 (A2)；
没有 L1 的命名空间 (A12)，L2 的 ref 引用 (A3) 就会指向一团乱麻；
没有 L2 的参数校验和静态裁剪 (A6, A8)，L3 的冻结 (A7) 就锁住的是一个充满运行时炸弹的废案。

### 2、Stage 与 Probe 的关系：1:1 还是 1:N？
**裁决：严格 1:N。一个 Stage 对应一个连贯动作，但必须有 N 个正交的观测探针来交叉验证。**
你提的“代码管理”例子极其典型，但它恰恰暴露了一个认知陷阱：**把“业务流水线”错当成了“原子工序”。**
Git 提交、分支合并、解决冲突、推送远程——这绝对不应该是**一个** Stage。如果它们是一个 Stage，一旦 AI 在“解决冲突”时搞砸了，前面已经 commit 的代码和后面没 push 的代码，会让状态机陷入极其恶心的半成品状态。
**正确的拆解方式（OpenXenon 的最佳实践）：**
每个 Stage 应该是一个**最小闭环的原子动作**。
```yaml
stages:
  - id: commit
    action: { command: "git add . && git commit -m 'feat: {{task_desc}}'" }
    probes:
      - ref: oxn/exec-exit-zero  # 探针1：命令本身是否成功
        params: { command: "git log -1 --oneline | grep -q 'feat:'" }
      - ref: oxn/fs-not-exists   # 探针2：是否遗留了未暂存的冲突标记
        params: { pattern: "**/<<<<<<< HEAD" }
  - id: resolve-conflicts # 只有需要时才路由到这个 Stage
    action: { instruction: "解决当前分支的冲突，不要破坏既有逻辑" }
    probes:
      - ref: oxn/fs-not-exists
        params: { pattern: "**/<<<<<<< HEAD" }
  - id: push
    action: { command: "git push origin {{branch_name}}" }
    probes:
      - ref: oxn/exec-exit-zero
        params: { command: "git status -sb | grep -q '[ahead 0]'" } # 确保真正推上去了
```
**结论：** Stage 是对 AI 的一次“指令下发”，Probe 是对这次指令结果的“多维度取证”。1 个动作，N 个视角，这才是可靠的裁决。

### 3、Probe 追加：位置隐式追加 vs 显式 `probes_append`
**裁决：坚决拒绝基于位置的隐式追加，必须显式声明 `probes_append`。**
你的提议很符合 Unix 直觉，但违背了 OpenXenon 的核心宪法：**Blueprint 必须是完整的真相源。**
假设 AI 写了一个 Blueprint，里面只有 `ref: oxn/stages/install`，没有写任何追加探针。如果仅仅因为 `.openxenon/tasks/xxx/` 目录下存在一个同名探针文件，Core 就自动把它追加进去，这会导致极其可怕的后果：
1. **不可复现**：换一台机器跑同一个 Blueprint，因为本地没有那个临时探针，结果完全不同。
2. **审查失明**：人类审查 Blueprint YAML 时，根本不知道系统偷偷塞了一个探针。
3. **AI 越狱**：AI 故意在 task 目录下伪造一个同名但永远返回 true 的探针文件，绕过所有校验。
**因此：位置（三层寻址）决定的是“探针代码从哪里加载”（身份解析），而不是“探针是否生效”（组合逻辑）。** 
组合逻辑（追加还是覆写）必须在 Blueprint 中显式声明。
---
### 4、版本化/Shadowing 与位置寻址的关系
这两个概念**正交且互补**，绝无重复。
- **三层寻址 (A4) + Shadowing (A9)**：解决的是**“我是谁”**（身份解析）。
  - `ref: oxn/fs-exists` -> 找到了官方的探针。
  - `ref: ./fs-exists` -> 找到了项目级同名探针，发生了 Shadowing（覆写身份）。
- **资产版本化 (A7)**：解决的是**“我活在哪个时间”**（时间冻结）。
  - 提交任务时，把解析出的身份（不管是官方的还是 Shadowing 的）深拷贝锁死。
**如果要在 Shadowing 里“修改”探针？**
这正是 Shadowing 的意义！全局 Arsenal 里的 `oxn/fs-exists` 太严格，你在项目级 `.openxenon/arsenal/probes/fs-exists.yaml` 里写了一个宽松版。这就叫 Shadowing 修改。
然后在 Blueprint 里，你通过 `probes_append` 引用它：
`- ref: ./fs-exists` （追加一个本地修改版探针）。

### 5、生命周期流程图（终审版）
这是融合了所有 13 条原则后，一个 Task 从提交到执行裁决的完整物理流程：
```text
[工程师/AI] 执行 oxn task submit --blueprint deploy.yaml
      │
      ▼
┌─────────────────────────────────────────────────────┐
│ Phase 1: 实体解析 (L0, L1 层)                        │
│  1. 校验 1:1 锁死 (A1)                              │
│  2. 解析 Blueprint 中的 Stage ref (A2)               │
│  3. 执行三层寻址 (项目 > 全局 > 内置) (A4, A12)     │
│     └─ 若发现项目级覆盖全局级，标记 shadow=true      │
└─────────────────────────────────────────────────────┘
      │
      ▼
┌─────────────────────────────────────────────────────┐
│ Phase 2: 静态组合与校验 (L2 层)                      │
│  1. 处理 probes_append / probes_override (A3, A5)    │
│  2. 校验 params_schema，注入参数到模板 (A3, A8)      │
│     └─ 模板中含有逻辑运算(如三元)？直接报错熔断！    │
│  3. 对 condition 进行求值，不满足的探针物理删除 (A6) │
│  4. 检查平铺结构完整性 (A11, A10)                    │
└─────────────────────────────────────────────────────┘
      │
      ▼
┌─────────────────────────────────────────────────────┐
│ Phase 3: 物理冻结 (L3 层)                           │
│  1. 将所有引用展开为内联代码                         │
│  2. 注入 _xenon_meta (记录 ref, shadow, hash) (A9)  │
│  3. 生成 blueprint.frozen.yaml 并写入磁盘 (A7, A13) │
│  4. 打印血缘报告给终端 (供人类审查)                  │
└─────────────────────────────────────────────────────┘
      │
      ▼
[Core 下发指令] task next -> 返回 Stage (action + target)
      │
      ▼
[AI 劳工] 执行动作，产出代码/文件
      │
      ▼
[Core 裁决] 执行该 Stage 的 N 个 Probes (1:N 逻辑)
      │
      ├─ 全部 PASSED -> 追加写入 task-trace.yaml, 路由到下一 Stage
      │
      └─ 任一 FAILED -> 追加写入 task-trace.yaml, 熔断 Task
```
**审查要点：**
在这个流程中，没有任何“运行时的隐式魔法”。所有的组合逻辑（追加/覆写）、条件分支（静态裁剪）、身份溯源，都在 Phase 1-3 的“编译期”完成了。当任务真正开始跑的时候，它面对的是一个**绝对确定、不可篡改、无二义性的 `frozen.yaml`**。
这就是工程学与魔法的区别。你可以开始写代码了。
