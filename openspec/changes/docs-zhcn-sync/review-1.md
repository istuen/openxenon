这份架构方案极其精准地抓住了 OpenXenon 的分层本质！将 OXN DSL 沉降到 L1 与 Infra 并列，是一个极具洞见的决定：**它们都是 Kernel 的“基础设施”，只是一个提供物理运行能力，另一个提供语义解析能力。**
针对你的两个待确认问题，以下是终局裁决与深度剖析：
---
### 待确认 1：目录名称体系统一
**问题**：`forge` 对应 `forges/`，而 `promote` 对应 `arsenal/`，名称体系不统一。
**裁决：必须统一！解耦“模块名”与“目录名”。**
当前的混淆源于把**模块名** 和**资产状态目录名** 混为一谈。
- **Arsenal** 是 L2 的领域模块，它管理资产的完整生命周期。
- 在这个生命周期中，资产有两个物理状态：**草稿** 和 **正式**。
**终局方案：引入 Armory（军械库）概念**
| 生命周期阶段 | L2 操作模块 (属主)           | 资产状态 | 宿主物理目录 (L1 Infra 管理) |
| :----------- | :--------------------------- | :------- | :--------------------------- |
| 打造阶段     | **Forge** (Arsenal 子模块)   | 草稿     | `.openxenon/forges/`         |
| 提升阶段     | **Promote** (Arsenal 子模块) | 正式     | `.openxenon/armory/`         |
**为什么用 `armory/` 替代 `arsenal/`？**
在军事术语中，Arsenal 是一个抽象的“兵工厂体系”，而 Armory 是具体存放成熟武器的“军械库”。`.openxenon/armory/` 完美表达了“经检验可用的正式资产存放地”，且与 `forges/`（锻造车间）在隐喻和命名格式上形成了完美的对仗。
---
### 待确认 2：“资产”属于 L1 还是 L2？
**问题**：资产（Blueprint, Part, Probe, Work）是 OXN DSL (L1) 的体现，还是独立的 L2 层？
**裁决：资产属于 L2 的核心概念，L1 只是资产的“铸造模具”与“运输通道”。**
这涉及一个极其重要的架构哲学：**区分“语言”与“用语言写出的文章”。**
1. **L1 OXN DSL 的本质**：它是**语法规范**、**解析器** 和 **序列化器**。它定义了什么是合法的名词和动词，但它本身不承载业务。就像 JSON Schema 和 `JSON.parse()`，它们不等于你业务里的那个 `User` 对象。
2. **L2 Arsenal/Work 的本质**：它们是**资产的实例** 和 **生命周期管理者**。Blueprint、Part、Probe 是用 OXN DSL “写出来的文章”，它们承载了具体的领域价值。
**架构流转关系**：
```text
L2 Arsenal 发出指令 → 调用 L1 OXN DSL 解析文本 → 提取出纯数据 (L0 Schema) 
→ L2 基于这些数据构建出资产对象 → 交由 L2 Work 执行
```
如果将资产放在 L1，会导致 DSL 层沾染业务逻辑（比如资产的状态流转、版本比对），这会彻底摧毁 DSL 作为“纯解析基建”的通用性。**L1 提供肉身，L2 赋予灵魂。**

## 三、裁决两个待确认问题
### 问题 1：Forge vs Promote 目录命名统一
**现状**：
```
.openxenon/
├── forges/          ← Forge 产物 (Draft 阶段)
└── arsenal/         ← Promote 产物 (正式阶段)
```
**问题**：模块叫 Arsenal，但只有 Promote 阶段才进入 `arsenal/`，Forge 在 `forges/`。概念割裂。
**裁决：统一为 Arsenal 内部的两阶段子目录**
```
.openxenon/
└── arsenal/
    ├── drafts/          ← Forge 产物 (草稿阶段)
    └── canonical/       ← Promote 产物 (正式资产)
```
**理由**：
| 维度   | 旧方案                                      | 新方案                                                   |
| ------ | ------------------------------------------- | -------------------------------------------------------- |
| 语义   | `forges/` 暗示"锻造厂"，与 Arsenal 主题脱节 | `arsenal/drafts/` 明确表示"武库中的草稿"                 |
| 归属   | Forge 和 Promote 似乎操作不同系统           | 统一在 Arsenal 下，Forge 和 Promote 是同一系统的两个阶段 |
| 一致性 | 模块叫 Arsenal，目录叫 forges/              | 模块叫 Arsenal，目录也叫 arsenal/                        |
| 扩展性 | 未来加新阶段需要新建顶级目录                | 新阶段只是 arsenal/ 下的新子目录                         |
**对应 CLI 命令**：
```bash
oxn forge probe Http          → 写入 .openxenon/arsenal/drafts/probe-Http.oxn
oxn promote probe Http        → 移动到 .openxenon/arsenal/canonical/probe-Http.oxn
```

### 问题 2：资产的本质归属——L1 还是 L2？
这是整个架构中最深刻的哲学问题。让我用一张图说清：
```
┌──────────────────────────────────────────────────────────┐
│                    "资产" 的本质                          │
│                                                          │
│  L1-OXN DSL 定义了 "什么是资产" (物种定义)               │
│  ┌──────────────────────────────────────────┐            │
│  │  Grammar:  probe name=ID { params=... }  │            │
│  │  Parser:   文本 → AST                     │            │
│  │  Validator: AST → Kernel Schema           │            │
│  │                                          │            │
│  │  这是资产的"基因"——定义了 Probe 长什么样   │            │
│  └──────────────────────────────────────────┘            │
│            │ 解析产出                                     │
│            ▼                                              │
│  L0-Kernel Schema 定义了 "资产的数据结构" (骨架)          │
│  ┌──────────────────────────────────────────┐            │
│  │  PartDefinition { name, probes[], ... }   │            │
│  │  ProbeDefinition { name, ref, params }    │            │
│  │                                          │            │
│  │  这是资产的"骨架"——所有层共享的数据契约    │            │
│  └──────────────────────────────────────────┘            │
│            │ 实例化                                       │
│            ▼                                              │
│  L2-Arsenal 管理了 "资产的实例" (个体管理)                │
│  ┌──────────────────────────────────────────┐            │
│  │  Forge:   创建 draft-Http-Probe.oxn      │            │
│  │  Promote: 提升 → canonical-Http-Probe.oxn│            │
│  │  Load:    读取 → PartDefinition 实例      │            │
│  │                                          │            │
│  │  这是资产的"动物园"——管理具体的资产个体    │            │
│  └──────────────────────────────────────────┘            │
└──────────────────────────────────────────────────────────┘
```
**裁决：资产跨越三层，但核心定义在 L1-OXN DSL**
| 层级                 | 对资产的职责                                    | 类比           |
| -------------------- | ----------------------------------------------- | -------------- |
| **L0-Kernel Schema** | 定义资产的数据骨架（`PartDefinition`）          | 物种的骨骼图   |
| **L1-OXN DSL**       | 定义资产的表达方式和校验规则（语法→Schema映射） | 物种的基因密码 |
| **L2-Arsenal**       | 管理资产的实例生命周期                          | 物种的个体管理 |
**关键洞察**：
> **OXN DSL 不只是"语法前端"，它是 Kernel Schema 的具体实现。**
> Kernel 定义了"什么是 PartDefinition"（抽象），OXN DSL 定义了"如何写出 PartDefinition"（具体）。
> Arsenal 只是 OXN DSL 产物的管理者。
**因此，"资产"这个概念的主键在 L1-OXN DSL，而非 L2-Arsenal。**
但 Arsenal 仍然是 L2 独立模块，因为：
1. 资产管理需要 IO（依赖 L1-Infra）
2. 资产管理涉及业务流程（Forge→Promote→Load 状态机）
3. 这些职责不属于 L1（L1 不碰 IO，不做业务流程）
---
### 最终层级架构定义
```
L0  Kernel        纯真空引擎
    Schema        数据契约 + 校验规则
    Contract      向外请求能力的纯净接口
    Processor     零 IO 的纯逻辑推演
L1  Foundation    基座层
    Infra         宿主环境适配 + 副作用收口
    OXN DSL       领域语言 = 资产的定义层 (Grammar/Parser/Validator/Serializer)
L2  Domain        领域层
    Arsenal       资产实例管理 = 资产的管理层 (Forge/Promote/Load)
    Work          任务执行单元 = 资产的使用层 (Plan/Task/Explore)
L3  Runtime       运行时入口
    CLI           外部指令集 (工程师 + AI)
    Daemon        内部后台进程 (监控 + 逃逸检测)
    Skill         AI 技能适配 (调起 AI 模型)
    Hall          研讨厅 (未来视图层)
```
**一句话总结**：
> **L0 定义骨架，L1 定义物种，L2 管理个体，L3 驱动一切。**

两者共同构成了 Kernel（L0）赖以生存的两大基座。
以下是对两个待确认问题的终局裁决：
#### ⚖️ 待确认 1：Arsenal 命名体系统一（`forges/` vs `arsenal`）
**痛点**：Forge（动作/阶段）对应目录 `forges/`，Promote（动作/阶段）对应目录 `arsenal`。词性不对齐，状态不清晰。
**裁决：统一为“状态名词”，拒绝“动作名词”作为目录名。**
目录代表的是**实体的驻留地**，而不是**动作的发生地**。
- `forges/` 听起来像“锻造车间”，里面放的是正在被锻造的东西。
- `arsenal/` 听起来像“军械库”，里面放的是已经锻造好的东西。
**建议命名方案：**
- 将 `.openxenon/forges/` 重命名为 **`.openxenon/drafts/`**（草稿箱）或 **`.openxenon/staging/`**（暂存区）。
- 保留 `.openxenon/arsenal/`（正式库）。
这样，资产的阶段流转极其清晰：
`Draft (草稿)` —[Forge 动作]—> `Staging (暂存)` —[Promote 动作]—> `Arsenal (正式)`
目录结构：
```text
.openxenon/
├── drafts/       ← 存放 forge 产出但未 promote 的资产
└── arsenal/      ← 存放已 promote 的正式资产
```
**这既统一了命名体系（都是状态名词），又与代码层的 Forge/Promote 动词形成了完美的动名词映射。**
---
#### ⚖️ 待确认 2：资产（Blueprint/Part/Probe）到底在 L1 还是 L2？
**痛点**：Arsenal 只是资产管理模块，而资产本身是 OXN DSL 的体现。资产应该跟着 DSL 算 L1，还是跟着 Arsenal 算 L2？
**裁决：资产（作为运行时数据实体）必须在 L2！**
这是架构中最容易混淆的“形而上 vs 形而下”问题。我们需要区分**“资产的定义能力”**和**“资产的运行时实体”**：
1. **L1 - OXN DSL**：提供的是**资产的元模型与解析能力**。它就像编译器，知道语法规则，能把文本变成 AST。但编译器本身不是程序。
2. **L2 - Arsenal**：管理的是**资产的运行时实体**。它是被 DSL 解析出来的、活生生的数据对象，需要被寻址、加载、缓存、提升。
**为什么资产不能在 L1？**
- L1 是无状态的基座。如果资产在 L1，意味着 L1 需要理解“草稿”和“正式”的区别，需要管理资产的生命周期，甚至需要处理资产的寻址（去内存找还是磁盘找），这就导致 L1 退化为 L2，破坏了基座的纯粹性。
- 资产具有**物理状态**（是存在于内存的 Builtin，还是存在于磁盘的 Draft？），状态的变更必须依赖 Infra (L1)，而统筹这些状态的是 Arsenal (L2)。
**结论：**
- **L1 (OXN DSL)** 定义了 Blueprint/Part/Probe 的**语法和结构**。
- **L2 (Arsenal)** 持有和管理 Blueprint/Part/Probe 的**运行时实例和数据**。

### 🏁 核心流转总结
**编译流（读取）**：
`.oxn 文件` → **L1 Infra(读)** → **L1 OXN DSL(解析)** → `FrozenBlueprint` → **L0 Processor(推演)**
**变更流（写入）**：
`AI 意图` → **L3 CLI** → **L2 Arsenal(Forge/Promote)** → **L1 OXN DSL(CRUD Processor 计算 TextEdit)** → **L1 Infra(写)** → `.oxn 文件`
**执行流（运行）**：
**L3 Daemon/CLI** → **L2 Work(调度)** → **L0 Processor(判决)** → (需外部信息时) → **L0 Contract** → **L1 Infra(实现)**
按此宪法重构，OpenXenon 的代码将如水晶般清澈，L0 绝对真空，L1 左右逢源（左接语义，右接物理），L2 掌控流转，L3 触达万物！
