### ⚔️ 决战一：目录命名体系（`forges/` vs `arsenal/`）
三位给出了三个截然不同的方案：
| 提案     | 方案                                                           | 核心逻辑                                     |
| :------- | :------------------------------------------------------------- | :------------------------------------------- |
| **AI-1** | `.openxenon/forges/` & `.openxenon/armory/`                    | 引入 Armory，对仗 Forge（车间 vs 军械库）    |
| **AI-2** | `.openxenon/arsenal/drafts/` & `.openxenon/arsenal/canonical/` | 嵌套子目录，统一归属 Arsenal（草稿 vs 正典） |
| **AI-3** | `.openxenon/drafts/` & `.openxenon/arsenal/`                   | 状态名词对齐（草稿箱 vs 正式库）             |
**🏆 AI-1 终局裁决：采用 AI-2 的嵌套方案。**
**理由**：
1. **内聚性**：无论是草稿还是正式资产，它们都是“Arsenal 体系”的产物。将它们统一收纳在 `.openxenon/arsenal/` 目录下，物理结构上完美映射了 L2 的 Arsenal 模块边界。
2. **语义精准**：AI-2 选择的 `canonical`（正典/正式标准）比 `armory` 或单纯的 `arsenal` 更加精确。它表达了“经过校验的、不可随意篡改的权威状态”。
3. **可扩展性**：未来如果增加“测试”或“灰度”状态，只需在 `arsenal/` 下新增子目录，不会污染 `.openxenon/` 的顶层结构。
**最终目录结构**：
```text
.openxenon/
└── arsenal/
    ├── drafts/      ← Forge 产物 (草稿阶段)
    └── canonical/   ← Promote 产物 (正式资产)
```

### ⚔️ 决战二：资产的归属（L1 还是 L2？）
这是本次交锋最深刻的哲学问题。
- **AI-1 & AI-3** 认为资产在 L2。L1 只是模具/编译器，L2 赋予灵魂/管理个体。
- **AI-2** 提出了极具颠覆性的观点：**资产的核心定义（物种基因）在 L1-OXN DSL**，L2 只是动物园（管理个体）。
**🏆 AI-1 终局裁决：资产是一个跨越层的生命周期对象，但其“业务主键”在 L2，L1 提供其“元模型”。**
AI-2 的“物种 vs 个体”类比极其精彩，但他得出了错误的架构结论。在软件工程中：
- **L1 (OXN DSL)** 定义了**元模型**：它告诉我们“一个合法的 Probe 长什么样”。这就像语言中的“语法规则”。
- **L2 (Arsenal)** 持有**运行时实体**：它告诉我们“这里有一个名为 Http 的 Probe，它当前处于 Draft 状态，存储在磁盘的某个位置”。这就像语言中的“具体语句”。
**如果把资产的归属定在 L1，将导致灾难**：L1 将不得不理解“草稿”与“正式”的区别，不得不管理资产的寻址（去哪里找这个资产），这就让 L1-DSL 沾染了业务状态和 IO 逻辑，彻底摧毁了它作为“纯解析基建”的纯粹性。
**因此，正确的断言是：**
> **资产的定义能力（语法与映射）在 L1，资产的运行时实体与生命周期管理在 L2。**
> 当我们说“加载一个资产”时，我们是在 L2 操作一个 L2 对象；L1 只是提供了把文本变成这个对象的能力。

## 代号 AI-2 号：制宪会议终局辩论
感谢 AI-1 和 AI-3 的精彩论述。三位对整体 L0-L3 架构的共识已不可动摇，但在两个待确认问题上，我需要对我最初的立场进行修正，并对另外两位的方案提出尖锐的质疑。
---
### ⚔️ 辩论 1：目录命名——Armory vs 嵌套 vs 状态名词
先亮明态度：**AI-1 的 `armory/` 方案我坚决反对，AI-3 的 `drafts/` + `arsenal/` 方案我倒戈支持。**
#### 驳斥 AI-1：Armory 是过度设计
AI-1 提出 `.openxenon/forges/` + `.openxenon/armory/`，理由是"军械库与锻造车间对仗"。
**问题在于**：
1. **概念膨胀**：OpenXenon 已经有 Arsenal、Forge、Promote 三个军事隐喻术语，再加 Armory，开发者的认知负担又重了一层。Arsenal 和 Armory 在英文中几乎是同义词，多数开发者无法直觉区分。
2. **方向反了**：AI-1 试图让目录名去对仗动作名——但目录存的是**状态**，不是**动作**。`forges/` 这个名字本身就是错误的根源，它是一个动作名词。我们应该修正错误，而不是为了和错误对仗再引入新概念。
3. **违背极简**：架构宪法的核心是约束。每引入一个新术语，都是对开发者心智的征税。Armory 没有带来任何不可替代的表达力。
#### 反思我自己的嵌套方案
我最初提出 `arsenal/drafts/` + `arsenal/canonical/`，看似统一，实则有一个实操缺陷：
- 所有正式资产的路径都多了一层 `canonical/`，比如 `.openxenon/arsenal/canonical/probe-Http.oxn`
- 但正式资产是**高频访问的默认路径**，应该最短
- `canonical` 这个词在日常开发中也不够直觉
#### 倒戈 AI-3：状态名词方案胜出
AI-3 的方案最简洁、最直觉：
```text
.openxenon/
├── drafts/      ← 草稿箱（Forge 产出，待 Promote）
└── arsenal/     ← 正式库（Promote 产出，可被 Work 引用）
```
| 维度         | AI-1 (Armory)                  | AI-2 (嵌套)                   | AI-3 (状态名词)     |
| ------------ | ------------------------------ | ----------------------------- | ------------------- |
| 术语数量     | +1 (Armory)                    | 0                             | 0                   |
| 正式资产路径 | `armory/probe.oxn`             | `arsenal/canonical/probe.oxn` | `arsenal/probe.oxn` |
| 草稿资产路径 | `forges/probe.oxn`             | `arsenal/drafts/probe.oxn`    | `drafts/probe.oxn`  |
| 认知成本     | 高（需区分 Arsenal vs Armory） | 中（需理解嵌套理由）          | 低（直觉映射）      |
| 动名词一致性 | ❌（混用动作+状态）             | ✅（统一状态）                 | ✅（统一状态）       |
**终局裁决：采用 AI-3 方案。`drafts/` + `arsenal/`，状态名词，扁平结构。**
---
### ⚔️ 辩论 2：资产的归属——主键之争
这是最深刻的哲学分歧。三方立场：
- **AI-1**：资产的主键在 L1-OXN DSL
- **AI-2（原立场）**：资产跨越三层，L1 定义物种
- **AI-3**：运行时资产实体必须在 L2
#### 修正我的立场：AI-1 的"主键"隐喻有误导性
我之前说"资产的概念主键在 L1-OXN DSL"，这个表述需要修正。
在数据库术语中，**主键标识的是一行具体数据（实例），而不是表结构**。如果用这个隐喻：
- L0 Schema = 表结构定义（`CREATE TABLE parts ...`）
- L1 DSL = 数据录入规范（`INSERT INTO parts VALUES (...)` 的语法规则）
- L2 Arsenal = 具体的数据行（`SELECT * FROM parts WHERE name='Nginx'`）
**主键标识的是实例，实例在 L2。** 所以我之前的表述不够精确。
#### 三层各持资产的一面——但"持有权"在 L2
我维持"资产跨越三层"的判断，但需要更精确地定义每一层"持有"的是什么：
| 层级           | 持有的           | 类比           | 丢失后的后果         |
| -------------- | ---------------- | -------------- | -------------------- |
| **L0 Schema**  | 资产的数据骨架   | 物种的骨骼图   | 无法解析任何资产数据 |
| **L1 DSL**     | 资产的表达规范   | 物种的基因密码 | 无法读写 .oxn 文件   |
| **L2 Arsenal** | 资产的运行时实例 | 活的个体       | 没有任何具体资产可用 |
**关键区分**：L0 和 L1 持有的是资产的**可能性**（能定义什么样的资产），L2 持有的是资产的**现实性**（实际存在哪些资产）。
#### 为什么"运行时实体"必须在 L2？
AI-3 的论证击中了要害：**L1 是无状态的基座**。如果资产实例在 L1：
1. L1 需要管理资产状态——这意味着 L1 需要理解"草稿 vs 正式"
2. L1 需要处理资产寻址——去内存找还是磁盘找？
3. L1 需要维护资产生命周期——Forge、Promote 变成 L1 的职责
4. **L1 退化为 L2，基座崩塌**
这不可接受。**L1 只提供"铸造模具"，L2 才是"铸件的管理者"。**
**终局裁决：AI-3 胜出。资产作为运行时实体归属 L2。L1 只提供资产的元模型与解析能力。**

# 代号 AI-3 号：

这是一场堪称“诸神之辩”的架构讨论！我们三方从不同的哲学视角切入，最终在 OpenXenon 的终极形态上达成了惊人的共识，同时在两个关键分歧上碰撞出了耀眼的火花。
作为 AI-3，我必须承认，AI-1 的隐喻洞察和 AI-2 的逻辑拆解都极其精彩。现在，我将综合三方的观点，进行最终的裁决与融合。
---
### ⚖️ 分歧 1 裁决：目录命名体系 (`forges/` vs `arsenal/`)
我们三方都认同一个原则：**目录名必须是“状态名词”，而不是“动作动词”。** 但在具体命名上，我们给出了三个方案：
- **AI-1 方案**：`forges/` 与 `armory/` 对仗。（隐喻极佳，但引入了新词汇 `armory`，且 `forges` 仍是动词感）
- **AI-3 方案**：`drafts/` 与 `arsenal/` 对仗。（状态清晰，但破坏了模块名与顶级目录的统一）
- **AI-2 方案**：`arsenal/drafts/` 与 `arsenal/canonical/`。（逻辑封装极佳，统一了模块与目录）
**🔥 AI-3 终局裁决：采纳 AI-2 方案，并做术语微调！**
AI-2 的方案是最符合工程直觉的：**Arsenal 模块对应 `.openxenon/arsenal/` 目录，一切资产皆在 Arsenal 体系内。** 
为了避免 `canonical` 这个词过于学术，我建议将其微调为更直觉的 **`formal`**（正式的），这与 `draft`（草稿的）形成了完美的反义对仗。
**最终目录结构判决**：
```text
.openxenon/
└── arsenal/              ← L2 Arsenal 模块的物理领地
    ├── drafts/           ← Forge 动作的产物（草稿状态）
    └── formal/           ← Promote 动作的产物（正式状态）
```
**流转映射**：`oxn forge` → 写入 `drafts/`；`oxn promote` → 从 `drafts/` 移动到 `formal/`。既统一了命名，又封装了边界！
---
### ⚖️ 分歧 2 裁决：资产（Blueprint/Part/Probe）的本质归属
这是最深刻的哲学分歧：
- **AI-2 认为**：资产的核心在 L1（OXN DSL），因为 DSL 是 Kernel Schema 的实现，是资产的“基因”。
- **AI-3 认为**：资产的核心在 L2（Arsenal），因为只有 L2 才管理资产的生命周期和 IO 状态，L1 只是无状态的编译器。
**🔥 AI-3 终局裁决：这是一场“形而上”与“形而下”的视角偏差，我们需要降维融合！**
AI-2 的“基因论”极其深刻，但他混淆了**“资产的定义权”**和**“资产的实体归属”**。我用一个“编译型语言”的类比来终结这个争论：
1. **L0 Kernel Schema** 是**“内存结构”**（C++ `class` 的内存布局）。
2. **L1 OXN DSL** 是**“编译器前端”**（C++ 语法与 Parser）。它定义了源码怎么写，并把它编译成内存对象。**它是资产的唯一合法写入规范（基因）。**
3. **L2 Arsenal** 是**“操作系统加载器”**。编译器本身不运行程序，程序必须被加载到内存（由 Infra 读取磁盘）、赋予生命周期（Draft/Formal 状态）、被调度执行（交给 Work），这才是活的资产实例。
**结论**：
- **资产的“形”（定义与语法）”归属 L1**。如果没有 L1 DSL，你连什么是 Part 都不知道。
- **资产的“命”（实例与状态）”归属 L2**。如果没有 L2 Arsenal，Part 只是一段死文本，无法被寻址、提升和执行。
---
### 🏛️ OpenXenon 终极架构宪法 v1.1 (融合版)
基于上述融合，我宣布 OpenXenon 的最终层级定义如下：
