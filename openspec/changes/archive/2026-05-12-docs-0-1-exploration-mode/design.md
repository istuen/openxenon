## Context

当前 OpenXenon 处于 0.1 探索阶段，但文档（architecture.md v1.1 和 README.md）措辞像成熟产品文档：

- architecture.md 标题："版本 1.1，物理学定稿"
- README.md 开头："面向大语言模型的工程化控制引擎"
- 大量 0.2+ 的目标特性（Daemon 裁决、ESLint 铁丝网、逃逸检测）在文档中描述为已实现

这导致新工程师阅读文档后产生错误预期。文档需要反映 0.1 的真实状态：**可用的最小原型，不是缩水的 1.1**。

## Goals / Non-Goals

**Goals:**

- 让文档准确反映 0.1 的实际能力和架构
- 明确区分 0.1 已实现 vs 0.2 目标
- 建立"探索型文档"范式：假设清单 → 验证指标 → 结论

**Non-Goals:**

- 不修改任何代码实现
- 不改变 CLI 命令签名或行为
- 不为 0.2+ 功能编写详细设计（仅标注为"目标"）

## Decisions

### 决策 1：README.md 改版为核心入口

**选择**：将 README.md 从"定性宣传"改为"探索状态仪表盘"

**理由**：
- README.md 是新工程师的第一接触点，必须准确反映项目状态
- "探索阶段"标签 + 核心假设表比"控制引擎"更能帮助决策者理解项目性质
- L1/L2/L3 自举定义让贡献者知道"0.1 成功"的确切含义

**替代考虑**：
- 保持 README.md 为简单宣传页，在 architecture.md 中详细说明 → 拒绝，因为工程师通常只看 README

### 决策 2：architecture.md §5 重写为核心架构章节

**选择**：§5 从"Daemon-center 描述"改为"双模式架构（CLI-direct vs Daemon）"

**理由**：
- §5 是架构文档最核心的章节，必须反映实际运行模式
- CLI-direct 是 0.1 的核心价值（不依赖 Daemon 也能跑），应该显式说明
- Daemon 裁决作为 0.2 目标需要清晰标注，不能与 0.1 描述混淆

### 决策 3：版本号从 1.1 降级到 0.1

**选择**：architecture.md 版本改为"0.1 探索阶段"

**理由**：
- "1.1 物理学定稿"暗示系统已成熟，与实际不符
- "0.1"明确表示这是初始探索版本，预期会有重大变化
- 符合 semver 语义：0.x 表示 API 未稳定

### 决策 4：探索问题清单作为 §1.2

**选择**：新增"探索问题清单"章节，列出 Q1-Q6

**理由**：
- "我们还不知道 X 是否有效"比"我们确信 X 正确"更有价值
- Q5（"物理约束架构是否必要？"）是元问题，直接关联项目存在价值
- 问题清单让后续决策有据可依

## Risks / Trade-offs

| 风险 | 描述 | 缓解 |
|------|------|------|
| 文档更新后与代码脱节 | 文档描述的状态与代码实现产生新错位 | 建立 L2 自举验证流程，每次代码变更同步检查文档 |
| "探索阶段"标签降低可信度 | 外部人员可能认为项目不成熟不值得关注 | 在 README 明确"探索的是核心假设，核心架构已定" |
| 文档改动难以追踪 | 后续代码变更可能遗忘更新文档 | 将文档一致性纳入 code review 检查项 |
