```markdown
## 出发点

OpenXenon 建立在一个朴素的判断上：**给 AI 工程行为加约束，比不加好。**

AI 模型能快速探索、生成代码，但也会推测出错、出现幻觉。
工程师懂业务、懂技术，能设计方案、沉淀经验。
OpenXenon 想找到一种方式：把工程师的经验变成 AI 能理解并执行的约束，同时控制 Token 成本。

这个判断可能错。如果错了，至少我们能说清约束为什么没用——而不是模糊地觉得"AI 不靠谱"。
除此之外，没有更多假设。路是走出来的，不是论证出来的。
```

### Requirement: architecture.md §1.1 措辞调整

**FROM:**

```markdown
### 1.1 核心原则

OpenXenon 的设计建立在三大不可违背的物理学公理之上：

| 公理 | 内容 | 违反后果 |
|------|------|----------|
| **公理一** | AI 是不被信任的观测者 | 系统丧失事实基础 |
| **公理二** | Kernel 是盲目的判官（只做符号归约） | 系统丧失可验证性 |
| **公理三** | Infra 是唯一的物理出口（死守边界） | 系统丧失安全性 |
```

**TO:**

```markdown
### 1.1 架构原则

OpenXenon 采用分层架构，各层职责清晰：

- **Kernel（纯函数层）**：只做符号计算，不碰硬件，不搞状态
- **Infra（物理层）**：唯一触碰文件系统和进程的组件
- **CLI / Daemon（编排层）**：协调 Kernel 和 Infra，不含业务逻辑
```
