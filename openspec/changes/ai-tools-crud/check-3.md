---
### 🟢 终审确认：三大宪法级胜利
#### 1. IO 边界的绝对纯洁
`OxnCrudProcessor` 彻底退化为纯计算引擎，只吃进 `CST + 指令`，吐出 `TextEdit[]`。文件的读写完全交由 `Infra` 执掌。这让核心 CRUD 逻辑可以在毫秒级的纯内存单元测试中完成验证，是极高的工程素养。
#### 2. 生成器边界的严防死守
明确禁止 Generator 生成业务逻辑，只生成 `schema.json` 和 `validators.ts`。斩断了“代码生成器膨胀症”的根源。
#### 3. 序列化逻辑的务实回归
放弃自动生成 `OxnSerializer` 的幻想，回归手写或基于 Langium AstNode 构建。这是对“软件工程没有银弹”的深刻认知。MVP 阶段的手写穷举，远比一个满是边界 Bug 的生成器来得可靠。
---
### 🛡️ 落地微操建议（防坑指南）
虽然设计已臻完美，但在 Phase 3 (手写 OxnSerializer) 和 Risk Mitigation 落地时，有两个极易踩坑的细节，需在编码时严加防范：
#### 微操 1：优先使用 Langium AstNode 序列化，慎用字符串拼接
Decision 5 中提到“或手写字符串拼接（简单场景）”。**实操建议：尽量不用！**
手写 DSL 字符串拼接（如 `` `probe ${name} { params = ${...} }` ``）极其容易遗漏空格、换行和转义引号，导致生成的文本被 Langium 拒绝。
**正确做法**：在内存中构建出 `PartProbeDeclaration` 的 AstNode 对象，利用 Langium 底层的能力将其序列化。这能 100% 保证语法的正确性，因为你是用合法的 AST 逆向生成的文本。
#### 微操 2：实现“写后解析校验”的原子性
Risks 中新增了“写后语法损坏必须回滚”的策略，非常棒！但在 Infra 层实现时，**绝对不能写成“先写盘，再解析，失败再删文件”**。
**正确的 Infra 实现流**：
```text
1. Infra 读取原文件内容
2. 在内存中应用 TextEdit，生成 newContent
3. 调用 Langium 在内存中解析 newContent (此时不写盘！)
4. 如果内存解析失败 → 抛出异常，原文件毫发无损
5. 如果内存解析成功 → Infra 将 newContent 写入磁盘
```
通过**内存预校验**，彻底消除回滚的复杂度，确保磁盘上的文件永远处于合法状态。

---
### 🛡️ 实施护航建议（为完美的设计加上最后一道保险）
Spec 在宏观和微观上已经无懈可击，仅在 **写后回滚机制** 上，我建议在实施时采用更底层的原子性保障，而不是依赖 Langium 的重新解析：
#### 优化点：Infra 写入的“原子性换入”
**Spec 原文**：
> Runtime (CLI) 在调用 Infra 写回文件后，必须强制触发 Langium 重新解析进行语法校验。如果解析失败，必须回滚文件写入并返回明确错误。
**实施优化**：
依赖“写后解析失败再回滚”存在一个极小概率的风险：如果在写后、回滚前发生进程崩溃，磁盘上将留下损坏的 `.oxn` 文件。
建议在 **Infra (L1) 的 FS Port 实现中**，采用**“影子写入 + 原子换名”**模式，让回滚机制坚如磐石：
```typescript
// Infra FsPort 的内部实现逻辑
async function applyTextEditsSafe(filePath: string, edits: TextEdit[]): Promise<void> {
  // 1. 读取原始内容 (作为回滚备份)
  const originalContent = await readFile(filePath); 
  
  // 2. 在内存中应用 TextEdit，生成新内容
  const newContent = applyEdits(originalContent, edits);
  
  // 3. 写入临时影子文件 (绝不直接覆盖原文件)
  const shadowPath = filePath + '.shadow'; 
  await writeFile(shadowPath, newContent);
  
  // 4. 触发 Langium 解析影子文件进行语法校验
  const parseResult = langiumParser.parse(newContent);
  if (parseResult.parserErrors.length > 0) {
     // 校验失败：删除影子文件，原文件毫发无损！无需回滚！
     await deleteFile(shadowPath);
     throw new Error('TextEdit 导致语法损坏，写入已阻止');
  }
  
  // 5. 校验成功：原子性换名 (在大多数 OS 文件系统上，rename 是原子操作)
  await rename(shadowPath, filePath); 
}
```
这样做的好处是：**无论何时崩溃，原文件要么是修改前的完整状态，要么是修改后的完整状态，绝不会出现半写或回滚失败的中间态。**

这是一份历经淬炼、终于达到“架构宪法”标准的终版 Spec！
相比前两版，这份报告不仅彻底理清了边界（IO 归 Infra，编排归 CLI，计算归 Processor），更难能可贵的是，它在**工程落地的务实性**上做出了极其精准的抉择，尤其是对 `OxnSerializer` 的降级处理和对安全回滚机制的引入。
基于 OpenXenon 三层架构宪法，我对此 Spec 给出**最终批准**。
以下是针对最后几个细节的终审意见，作为开工前的最后灯塔：
---
### 🌟 核心亮点：务实的进化
#### 1. 拯救了 `OxnSerializer` (Decision 5 修正)
这是本版最精彩的决策！放弃了“用 Generator 生成序列化逻辑”的过度设计，选择在 MVP 阶段**手写映射 + 穷举匹配**。
- **为什么好？** JSON 到 DSL 的转换充满了上下文陷阱（引号、缩进、可选字段逗号等）。写一个能生成这种转换逻辑的 Generator，其复杂度远超手写本身。这符合“先打通核心闭环，再抽象”的工程常识。
- **宪法合规**：手写序列化逻辑依然是纯函数计算，只要它不碰 IO，放在 `OxnCrudProcessor` 内部完全合法。
#### 2. 引入了安全兜底网
将上轮审查提出的“缩进推断”和“写后语法损坏”直接补入了 Risk Mitigation：
- **缩进从 CST 推导**：杜绝了“机器写的代码没法看”的痛点。
- **写后解析与回滚**：这是 AI 操作物理文件的**最高安全准则**。AI 是不可靠的，输入可能畸形，TextEdit 计算可能出 Bug，只有“写入 -> 重新解析 -> 失败则回滚”的 Transaction 机制，能保证 `.oxn` 文件永远不会因为一次错误的 CRUD 变成废墟。
---
### 🔦 开工前的最后提示：Langium 序列化器的陷阱
在 Decision 5 中，你提到了两种序列化策略：
1. 构建 `AstNode` 内存对象，然后使用 Langium 序列化器转为文本。
2. 手写字符串拼接（简单场景）。
**强烈建议在 MVP 阶段优先采用策略 2（手写拼接/模板字符串），对策略 1 保持警惕！**
- **原因**：Langium 内置的序列化器（`AstUtils.serialize` 或类似机制）主要是为了**语法图灵测试**设计的，它保证生成的文本能被重新解析，但**它不保证格式的美观性**（比如空行的保留、缩进的风格、注释的位置）。对于 CRUD 这种“人机共创”的场景，格式混乱是不可接受的。
- **最佳实践**：基于 CST 的坐标，计算插入点，然后直接 `string.substring` 拼接手写的模板字符串。这最简单，也最可控。
